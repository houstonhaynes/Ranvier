## Exact Ripple API and scheduling

- `Var.create initial` returns writable `Var<'T>`; read/write `.Value`. Sources use structural equality by default; `Var.createWith equality initial` changes cutoff.
- `Signal.computed (fun () -> ...)` creates a cached derived signal with tracked reads and structural cutoff; `Signal.map f source` and `map2 f a b` are alternatives. A Var is also a Signal.
- `Signal.effect (fun () -> ...)` runs immediately, reruns on dependencies, and returns `IDisposable`. `Signal.autorun` runs likewise but relies on its surrounding scope for disposal. `Signal.subscribe handler signal` passes current values and returns a handle.
- `Signal.batch (fun () -> ...)` defers effects until the outermost batch exits. `Signal.peek`, `.Peek()`, and `Signal.untracked` avoid tracked reads.
- `Signal.root (fun () -> value)` returns `value * IDisposable`; derived nodes/effects created synchronously inside belong to that scope. `Signal.onCleanup (fun () -> ...)` registers a scope cleanup.

These signatures and equality policies are in [Api.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Api.fs); immediate execution and ownership are documented in [effects/scopes](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/docs/content/ripple/effects.md) and [batching](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/docs/content/ripple/batching.md).

**Per-binding scheduling is synchronous.** `Html.text (fun () -> string source.Value)` constructs one persistent text node and one autorun, skips unchanged strings, and writes `nodeValue`. `Base.bindAttribute name callback` creates an autorun per attribute and skips unchanged strings. `attr.value (fun () -> text.Value)` uses `Base.bindProperty "value" callback`, an autorun assigning the live property with a previous-result check. These are not frame or microtask scheduled. After a normal source setter returns, affected binding writes have completed; inside batch, they complete before the outermost batch returns. The browser may paint later: DOM-settled timing is not paint timing. [Html.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple.Dom/Html.fs), [Base.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple.Dom/Base.fs), [Scheduler.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Scheduler.fs).

`on.click handler` and `on.input (fun (value:string) -> ...)` auto-batch their writes. Ranvier's current `Dom.on` restores graph/owner and uses untracked execution but does not itself add a batch. Use explicit equivalent batching in any multi-write common handler. [Events.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple.Dom/Events.fs), [local Ranvier Dom](../../src/Fable.Ranvier/Dom.fs).

## DOM construction, input, and cleanup

Ripple `Html.div [ ... ]` uses a single `DomItem list` for children, attributes, and event modifiers. `Html.text "static"` is static; thunk and signal overloads are reactive. `Html.mount "host-id" (fun () -> Html.div [...])` opens a root scope, constructs and appends one root, and returns `IDisposable`. The function argument matters: preconstructing a view before mount would create its effects outside the intended scope. The mount leaves pre-existing host children intact. Repeated disposal is a no-op; normal disposal tears down its scope then removes its root. [Html.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple.Dom/Html.fs).

Input current value is supported as a **property**, not a `value` attribute. `attr.value` plus typed `on.input (fun (value:string) -> ...)` is the documented manual pair; `attr.bindValue (Var<string>)` supplies both directions and internally casts to `HTMLInputElement`. `bindValue` assigns `.value` unconditionally when its effect runs, whereas manual `attr.value` checks its previous signal result. Neither is identical to Ranvier's user-supplied typed setter that compares the input's actual current `.value` before assignment. Probe caret preservation as correctness, and report differences; do not silently add a custom setter to Ripple to hide an observed failure. [Bindings docs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/docs/content/ripple-dom/bindings.md), [Attributes.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple.Dom/Attributes.fs), [Ranvier README](../../src/Fable.Ranvier/README.md).

Source inspection exposes lifecycle differences requiring browser verification:

- Ripple event helpers call `addEventListener` without a paired cleanup/removal. Removing a mounted node removes it from the live DOM but does not imply a retained detached node's listeners are gone. Ranvier registers listener removal with its owner cleanup.
- Ripple mount captures its original container and later calls `container.removeChild node`. Ranvier removes from the root's current parent. Moving a root before disposal is therefore not an equivalent supported contract without a probe.
- Ripple `Signal.root` restores its current-scope variable in `finally`, but has no exception catch disposing a failed factory's newly-created scope. Mount likewise lacks failed-construction cleanup. This suggests a leak when construction throws after creating an effect; it is a source-derived hypothesis pending runtime verification.
- Scope cleanup runs children first, then cleanup callbacks, then disposes tracked nodes. A throwing cleanup can interrupt this sequence. Do not assume exception-proof teardown.

[Ripple Scope.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Scope.fs), [Ripple Base.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple.Dom/Base.fs), [Ripple Html.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple.Dom/Html.fs), [Ranvier mount](../../src/Fable.Ranvier/Mount.fs).

## Fair common synchronous browser workload

Use ordinary HTML, a stable root/child structure, explicit text bindings, string attributes, live input properties, input/click events, synchronous source writes, derived values, batches, and mount/disposal. Ranvier's README states this PoC does not implement keyed reconciliation, dynamic subtree replacement, SVG, SSR/hydration, templates, or Solid scheduling. Ripple's broader renderer capabilities must not be presented as whole-product parity. [Ranvier scope](../../src/Fable.Ranvier/README.md), [Ripple element/control flow implementation](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple.Dom/Html.fs).

Construct **1,000 persistent text bindings in a static child list** in each renderer, with the same HTML depth, same signal fan-out, same derived function/string conversions, same write sequence, and same final values. For Ripple use ordinary `Html.div`/`Html.span` with `Html.text thunk`, not `Html.each`; for Ranvier use ordinary `Dom.element` children with `Dom.reactiveText`. This isolates stable-node propagation rather than comparing Ripple's keyed diff with a feature absent from Ranvier. Distinguish a shared-source 1,000-binding fan-out from 1,000 independent sources; report whichever is actually measured.

Time mount, single-write fan-out, an explicit batch of repeated writes, and disposal separately. Read/verify all resulting DOM values after each timed operation. Keep correctness instrumentation out of timing samples. Test no-op equality, derived cutoff, optional attribute removal (a custom Ripple Apply/autorun would be application glue and must be disclosed), initial text, input property roundtrip, independent mounts, repeated disposal, and post-disposal writes. Report unsupported/failed lifecycle probes separately from successful common-workload timings.

Use one browser/version, production bundles, identical Fable compiler/runtime dependencies when possible, warmup, enough independent samples, and explicit statistic definitions. Record build mode, package versions, workload size, emitted JS and gzip sizes, and whether timing ends at DOM state or at paint. Do not infer speed from implementation shape or from a different renderer's advertised benchmark.

## Async, promise nesting, and error baseline

Async is testable, but Ripple's own async guide explicitly describes **application code**, not a resource API. It models `NotAsked | Loading | Reloading of 'T | Loaded of 'T | Failed of string` and uses a mutable request generation so late successful and failed responses cannot overwrite a newer request. The guide's minimal example omits Failed; the first-party demo includes `Promise.map ... |> Promise.catch ...`, guarding both outcomes with the generation. There is no documented built-in cancellation, resource primitive, Suspense, or propagation of tracking/ownership across promises in this baseline. [Async guide](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/docs/content/ripple-dom/async-data.md), [full AsyncData demo](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/demo/Examples/Recipes/AsyncData.fs).

The demo opens `Fable.Core` for `Promise.create`, `Promise.map`, and `Promise.catch`, but its project explicitly references **Fable.Promise 3.2.0**. Namespace alone does not make those helpers part of the Ripple/core package dependencies. Include that package to compile the documented pattern literally. [Demo project](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/demo/Demo.fsproj), [dependency versions](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/Directory.Packages.props).

For a deterministic typeahead probe, substitute controlled deferred promises for the demo's timed request transport, retain its generation/error pattern, and keep stable text/status bindings rather than introducing keyed or dynamic DOM. Issue A, then B; resolve B before A, then test an older rejection, newest rejection, and refresh with retained previous data. Drain/await the returned promise chain before asserting DOM; a promise settling enqueues its continuations, unlike a synchronous setter. Separately measure propagation from an accepted async completion to settled DOM, excluding artificial transport delay. Disclose that stale-response protection/loading/error representation is application logic on Ripple.

The documented demo does **not** invalidate generation on owner disposal, cancel its timeout/transport, or prevent its promise callback from writing application state after unmount. Keep that baseline unchanged when testing disposal; do not add a disposed guard, AbortController, or cancellation shim to make it pass. Distinguish (a) detached DOM bindings stop because their scope was disposed, from (b) async work and callbacks cease, from (c) state stops changing. Only (a) follows from the documented root disposal contract. Failure of a stronger undocumented contract is a capability difference; an observed violation of a claimed contract is a defect.

Additional deterministic probes should cover nested promises (outer resolves to an inner pending promise), inner rejection, rejection thrown in success mapping, error recovery followed by a later successful request, disposal between outer and inner completion, and multiple pending generations. Record exact source/API used and exact output, including unhandled rejections. Do not convert a failing case into a success by rewriting its semantics after observing failure.

Tracking and ownership have a synchronous boundary in inspected code: `Tracking.recompute` restores its current tracker in `finally`; `Scope.root` restores its current scope in `finally`. Consequently a later promise callback reading a Var is not tracked by the initiating effect. `Signal.onCleanup` called after await/inside a later callback has no original current scope and silently registers nothing when no scope is active. That is a source-derived expectation, not a browser result. Probe an effect that reads only after promise completion and a late cleanup registration; do not claim async graph context propagation. [Tracking.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Tracking.fs), [Scope.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Scope.fs).

For synchronous exceptions, tracking context is restored and edge reconciliation occurs only on successful recomputation. Scheduler flush cleanup resets queue flags/guards, but explicitly drops remaining unvisited effects for that failed flush cycle. Probe both the direct exception and a later update's recovery; do not treat automatic error UI or continuation of all siblings as promised behavior. Promise rejection handling in the demo is the application's `Promise.catch`, not a graph-level error boundary. [Scheduler.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Scheduler.fs), [Tracking.fs](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Tracking.fs).

## Evidence limits

This research read local Ranvier adapter source and README and inspected Ripple package/source; it did not run semantic searches or modify F# code. All Ripple source links are pinned to the package commit. Browser correctness and timings are a subsequent step. Current source evidence supports a useful common DOM benchmark and a broader async capability probe, not full renderer equivalence or any performance ranking.
