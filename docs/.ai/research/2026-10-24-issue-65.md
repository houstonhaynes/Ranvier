# Issue #65: event sourcing adapters for traced builds

Research note for [#65](https://github.com/shayanhabibi/Ranvier/issues/65), "event sourcing adapters
for tracer builds". Repository facts are checked at `0967cc02` (branch `issue/65`, cut from
`integration/issues`); paths are relative to the repository root. The note builds on the research
comment posted on the issue on 2026-10-17, pinned to `66007fe` [C1], and re-checks it against the
current tree. Three of its prerequisites have since been split out and two have landed: #164 (cost
baseline, done), #165 (cursor and checkpoint, done, PR #178) and #166 (stable contracts, open).

## 1. The question

Can a traced Ranvier build feed an event store (Kafka, KurrentDB/EventStoreDB, Marten, Message DB),
and should Ranvier ship adapters for those stores? Inside that sit three questions:

1. **What is the event?** The trace log records engine work. Event sourcing stores domain facts.
2. **Which build pays?** A traced build costs 13x to 126x the untraced build (section 3.2).
3. **What does Ranvier own?** The store client, or the contract and the seam a client plugs into?

## 2. Answer in brief

- The trace log is a diagnostic log. Its events are fixed-shape engine records (`Write`, `Mark`,
  `CheckStart`, `RunStart`, `EdgeAdd`, ...) with `obj` payloads (`src/Ranvier/TraceEvents.fs`), and a
  dump writes a non-primitive payload as one line of at most 60 characters
  (`src/Ranvier/TraceModel.fs` L426, L499). A dump explains a run; it cannot rebuild values.
- Event sourcing in Ranvier is an **input journal**: signal writes from outside a computation,
  `AsyncSource.Settle`/`Fail`, and `Mvu` messages. Derived nodes recompute from the inputs. Replay
  re-runs the journal into a fresh graph, traced when the `why` history is wanted. Signal-map replay
  already works this way [R6].
- The input journal runs in the **untraced** build. Tracing is a replay-time choice, so the 13x to
  126x traced cost (#164) stays out of production.
- **Trace export** is the second, smaller tier: a sink over the #165 cursor (`Trace.eventsSince`) for
  development, CI and bounded diagnostic sessions.
- Ranvier owns the journal seam, the envelope and the back-pressure policy. Store adapters belong in
  separate packages or samples, because each store's policy (stream keys, expected-version
  concurrency, idempotent ids, schema registry) belongs to the application [E2][E3][E4][E5].

## 3. How it fits the current core

### 3.1 What has landed since the issue comment

| Comment option | Status at `0967cc02` | Where |

| 1. Cursor and checkpointed truncation | Done (#165) | `Trace.eventsSince` (`src/Ranvier/TraceApi.fs` L82), `Trace.checkpointOf` (L86), `Trace.checkpoint` (L415). Signal maps read by cursor (`docs/maps/SignalMap.fs` L849, L871). |
| Measure first | Done (#164) | `docs/content/benchmarks/tracing.md` L36–L101 |
| 2. Versioned contract, payload codec | Split out as #166 (open) | Node identity scopes, schema policy, codec seam, lossy marker |
| Payload codec | Available | `Ranvier.Wire`, `WireCodec<'T>` (`src/Ranvier.Wire/Types.fs` L46), one wire text on .NET and Fable; #68's note adopts it [C2] |
| 3. Input journal | Not started | This note, section 6 |
| 4. Trace export sink | Not started | This note, section 6 |
| 5. OpenTelemetry bridge | Not started | Deferred |
| 6. Store adapters | Not started | Out of core scope |

`eventsSince` copies only the events after the cursor and throws `ArgumentOutOfRangeException` for a
cursor before the checkpoint's seq (`TraceApi.fs` L73–L83); an expired consumer resyncs from
`checkpointOf`. `checkpoint` runs on the graph thread outside a flush, discharge or run, and
releases the dropped payloads (L400–L415). Together they give a sink a bounded log: drain, then
checkpoint the drained prefix.

### 3.2 What a traced build costs

From the #164 baseline (`docs/content/benchmarks/tracing.md`):

| Measure | Range |
| --- | --- |
| Steady-state update, traced / untraced | 13.6x (`cutoff`) to 89.0x (`signal`) (L68–L73) |
| Construction, traced / untraced | 115.9x to 189.2x (L77–L81) |
| Trace events per update | 14.0 (`memo`) to 392.1 (`fanout`, 64 memos) (L38–L39) |
| Log bytes per update, .NET | 879 (`memo`) to 18,186 (`fanout`) (L50–L51) |

An input journal records about one entry per user write, against 14 to 392 trace events per update.
Journal volume is one to two orders of magnitude below trace volume, and its hook can live in the
untraced build.

### 3.3 Entry points a journal hooks

| Input | Site | Notes |
| --- | --- | --- |
| Signal write | `Signal.Value` setter, `src/Ranvier/Core.fs` L3139–L3160 (`Tracer.Write` at L3152, L3159, L3172, L3177) | Journal only writes from outside a running computation; a computation's write is derived. |
| Async settle / fail | `AsyncSource.Settle` L3249, `Fail` L3264 | The result is the nondeterministic input; record it, as durable-execution systems record activity results [P3]. |
| Cross-thread work | `Graph.Dispatch` L2126, `Graph.DispatchAsync` L2191/L2203 (#167) | Replay feeds the journal through the dispatcher, in journal order. |
| `Mvu` message | `Mvu.Apply` / `Dispatch`, `src/Ranvier.Elmish/Mvu.fs` L37–L44 | Today only the resulting `root.Value` write is visible; the message, the domain event, is lost. |
| Graph configuration | `GraphOptions`, `src/Ranvier/Types.fs` L348–L367 | Four fields today; a journal would be a fifth, opt-in. |

The 64 `Tracer` hooks are `[<Conditional("RANVIER_TRACE")>]` and vanish from the untraced build
(`src/Ranvier/Trace.fs`). A journal hook is different: it must stay compiled in both builds, behind
a null check, and `tools/verify-trace.fsx` (the merge-base IL gate) will then report a deliberate IL
change in the untraced build. That change needs the user's agreement and a measured budget.

### 3.4 Ownership

Under `.claude/rules/view-uses-core.md`, scheduling, ownership and change detection belong to the
core. A journal is core state: it observes core inputs and replays through the core's dispatcher.
It adds no view-side state.

## 4. Prior art

| Source | What it settles |
| --- | --- |
| Fowler, Event Sourcing [P1] | "Capture all changes to an application state as a sequence of events"; gateways to external systems are disabled during replay. Ranvier's effects that call out are the gateways. |
| Elm / Redux time travel [P2] | Messages (actions) are the journal; the model is rebuilt by folding them. `Mvu` already has the shape. |
| Temporal event history [P3] | Activity completions are appended to a durable history, so replay uses recorded results instead of re-running them. Ranvier's async settles are the activities. |
| FsCodec [E6] | F# union cases as versionable event types; new fields as `option`, breaking changes as `V2` cases, upconversion in the codec. |
| Marten upcasting [E4] | Old event JSON is transformed on read, on the fly. |
| Confluent Schema Registry [E3] | Default `BACKWARD` compatibility: new consumers read old data; upgrade consumers first. |
| CloudEvents [E7] | Envelope attributes `id`, `source`, `specversion`, `type`; `source` + `id` unique per event. |
| KurrentDB, Message DB [E2][E5] | Expected-version append for optimistic concurrency; duplicate ids stored once (KurrentDB). |
| Kafka [E1] | Ordering per partition by key: one graph id per key keeps a graph's journal ordered. |
| Equinox [E8] | One F# codec over CosmosDB, DynamoDB, EventStoreDB, MessageDB; the lowest-effort F# route to many stores. |
| `System.Threading.Channels` [E9] | `BoundedChannelFullMode` `Wait`, `DropNewest`, `DropOldest`, `DropWrite`; under `Wait`, `TryWrite` returns `false` at once and only `WriteAsync` waits. |
| OpenTelemetry SDK [E10] | The batch processor drops spans past `maxQueueSize` (2048); samplers drop traces. A lossy channel, not a store. |

Sources E1–E10 were read for the issue comment on 2026-10-17 [C1]; P1 and P3 were read on
2026-10-24.

## 5. Options with costs

| # | Option | Cost | Benefit | Depends on |
| --- | --- | --- | --- | --- |
| A | **Input journal seam in core** (`IInputJournal` on `GraphOptions`; hooks at the section 3.3 sites; `Mvu` records messages) | Medium: one null-checked hook per input site in both builds, an IL-gate exception, a replay driver | Highest: event sourcing in production builds without tracing; serves #68 (snapshot plus tail) and #69's audit use case | #166 envelope, `Ranvier.Wire` codecs |
| B | **Trace export sink** (`ITraceSink` drained by cursor after each outermost flush, bounded channel, drop policy plus a gap event, then `checkpoint`) | Low–medium: uses #165 as is; no hot-path change | Medium: streaming diagnostics to files and CI; feeds #168's agent-observable graph | #165 (done), #166 |
| C | **Reference sinks** (JSONL file for both tiers, in-memory for tests) | Low | Proves A and B end to end | A, B |
| D | **OpenTelemetry bridge** (`ActivitySource` per root write, `why` summary as span events) | Low–medium | Medium: causality next to HTTP and DB spans | B |
| E | **Store adapters** (Equinox/FsCodec, Marten, Kafka, KurrentDB) as separate packages or samples | High and ongoing: a client dependency and release cycle each | Medium: turnkey persistence | A, #166 |
| F | **Journal outside core** (wrap writes in user code, `Mvu` wrapper, no core hook) | Low | Low: misses async settles and writes from bindings; unreliable replay | none |

Option F is the fallback if the user rejects any untraced IL change: it ships a journal for `Mvu`
messages alone, which covers the Elmish case but not raw signals.

## 6. Recommended scope

Scope #65 to **A + B + C**, as a spike that then graduates. Defer D until B exists, and E until a
user names a store; start E with an Equinox/FsCodec sample when it comes.

### 6.1 Input journal (option A)

Shape (names are proposals):

- `IInputJournal` with `Record : JournalEntry -> unit`. A `JournalEntry` carries the #166 envelope
  (`schema`, stream id, `seq`, `kind`, stable node key, `payloadType`, payload) and the encoded value.
- `GraphOptions.Journal : IInputJournal option`, default `None`.
- Journaled nodes are those with a stable application key (#166) and a `WireCodec<'T>`. A write to
  an unkeyed node, or one without a codec, is recorded as non-replayable, never silently dropped.
- `Mvu` records each message through its own codec before `Apply`.
- `Journal.replay : Graph -> JournalEntry seq -> unit` feeds entries through the dispatcher in order,
  with effects marked as replaying so gateways can skip external calls [P1].

Acceptance criteria:

1. A cart-sample test journals `Mvu` messages and external signal writes, replays them into a fresh
   traced graph, and the replayed final `Trace.snapshot` and the `Trace.why` output of every effect
   run equal the live traced run's, given journaled async results.
2. A property test: for any sequence of external writes, settles and failures, replaying the journal
   into a fresh untraced graph yields the same values for every keyed input and every memo.
3. Writes made by a running computation are not journaled; a test asserts it.
4. An unregistered payload produces an entry marked non-replayable, and `replay` fails with a named
   error on it.
5. With `Journal = None`, paired counters (`bench/Ranvier.Counters`, interleaved in one run) show the
   untraced `signal` and `memo` steady-state scenarios within the noise interval of the baseline;
   the only IL difference reported by `tools/verify-trace.fsx` is the guarded hook at the section
   3.3 sites, listed in the PR.
6. Fable: the same replay test passes under `build.fsx -- test-fable`.

### 6.2 Trace export sink (option B)

Shape: `Trace.export graph (sink: ITraceSink) (policy: SinkPolicy) : IDisposable`. After each
outermost flush, on the graph thread, it reads `eventsSince` from its cursor, encodes, and writes to
a bounded channel; a background task drains to the sink. With `CheckpointAfterDrain`, it calls
`Trace.checkpoint` at the drained seq once the sink acknowledges.

Acceptance criteria:

1. A stalled-sink stress test under a drop policy shows bounded process memory, and the exported
   stream holds a gap record naming the dropped seq range.
2. The same test under `Wait` loses no event, and the writer uses `WriteAsync` (or fails loudly on
   `TryWrite = false`) [E9].
3. Concatenating the exported events with the checkpoint header reproduces `Trace.dumpText` output
   for the same run.
4. The untraced build's IL is unchanged (`tools/verify-trace.fsx`).

### 6.3 Reference sinks (option C)

A JSONL file sink for both tiers on .NET, and an in-memory sink for tests on .NET and Fable. The
criteria in 6.1 and 6.2 run against them. No store client enters `src/Ranvier`.

## 7. Open questions for the user

1. **Untraced IL change.** The journal needs a guarded hook in the untraced build, which the
   merge-base IL gate currently forbids. Accept it with a measured budget, or keep #65 to option F
   (journal outside core, `Mvu` only)?
2. **Order against #166.** The envelope and node keys come from #166. Start #65 after #166 lands, or
   spike the journal with a provisional envelope now?
3. **Retitle the issue.** The recommended scope makes the adapters out of scope and the journal
   untraced. Rename #65 to "input journal and trace export", and file store adapters separately?
4. **Async determinism.** Record async results only (replay never re-runs async work), or also offer
   a mode that re-runs async work and checks its result against the journal?
5. **Shared snapshot with #68.** Should the journal's snapshot-plus-tail use #68's persisted-state
   format, so one restore path serves both?
6. **Milestone.** #65 sits in 1.0.0-rc (due 2026-10-31). The recommended scope is unlikely to land by
   then; move it out, or ship only the sink (option B) in the milestone?

## 8. User answers (2026-10-24)

1. **Untraced IL change: accepted.** The journal adds a guarded hook in the untraced build, within the
   budget of criterion 6.1.5.
2. **Order against #166: likely after #166.** #65 starts from #166's envelope and node keys.
3. **Retitle: probably.** Proposed title: "input journal and trace export"; store adapters are filed
   separately.
4. **Async results: both modes, chosen by the replay's intent.**
   - Diagnostic replay, which reproduces a run, feeds the journaled async results and never re-runs async
     work. Criterion 6.1.1 is this mode.
   - Re-enactment, which repeats a series of actions without requiring the same outcome, re-runs async
     work.
   - The journal therefore records async results in both cases, and `Journal.replay` takes the mode. The
     mode a sample or test defaults to depends on what each costs, measured once both exist.
5. **Shared snapshot with #68: accepted.**
   - #65 reuses #68's `StoredRecord` (key, version, Wire payload) and `IStateStore`.
   - A snapshot is the set of keyed input records at a journal position; restoring loads it and replays
     the journal entries after that position.
   - One condition: #166's stable node key and #68's application key are one key space.
   - One addition: #68's snapshot gains the journal position it was taken at.
   - The trace dump stays out of persistence, as #68's criterion H states.
   - #68 defines the format, and the journal consumes it.
6. **Milestone: split accepted.**
   - Options B and C (the trace export sink and the in-memory and JSONL sinks) ship in 1.0.0-rc. They add
     no hot-path change, and #165 and #166 are their only dependencies.
   - Option A (the input journal and replay) moves to the next milestone, because it depends on #68's
     format and on the untraced hook's measured budget.
