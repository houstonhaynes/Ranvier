## Prior art (primary sources)

Numbers refer to the source list at the end.

**Provider prompt caches reward a stable prefix.**

- Anthropic orders the cache prefix as `tools`, `system`, `messages`; a change at one level
  invalidates that level and every later one, and changing tool definitions invalidates the whole
  cache. A request has up to four breakpoints and a 20-block lookback [4].
- OpenAI caches by default on supported models, routes by a hash of the initial tokens, and treats
  `prompt_cache_key` as a routing hint, not a guaranteed hit [7].
- Manus reports cached input at 0.30 USD/MTok against 3 USD/MTok uncached on Claude Sonnet, an
  input-to-output ratio near 100:1, and calls KV-cache hit rate the most important production
  metric. Its practices: a stable prefix, append-only context, deterministic serialisation, and
  masking tools rather than removing them [5].

**Streaming UIs fight per-chunk re-rendering.** The Vercel AI SDK re-renders `useChat` on every chunk
by default and offers `experimental_throttle` [15]. `IChatClient.GetStreamingResponseAsync` returns
`IAsyncEnumerable<ChatResponseUpdate>` [16]. Vendor-reported decode rates reach 2,600 tokens/s
(Cerebras, Llama 4 Scout) [2], about one token per 385 µs.

**Incremental derived state at service scale exists.** Materialize maintains views incrementally and
serves them over a built-in MCP server [25][26]; CocoIndex and Pathway keep indexes current with
minimal recomputation [36][37]. Salsa's early termination [41] is the model for cross-run reuse. All
of these are services or persistent stores; none is an in-process graph that also drives a UI.

**Orchestrators are message-passing with checkpoints.** LangGraph runs Pregel-style super-steps
[42]; Microsoft Agent Framework checkpoints at superstep boundaries [43][44]. That is the agent loop,
and it is not Ranvier's shape.

Limits that shape the scope:

- Tracing is a whole-build switch: `RanvierTrace`, traced by default in Debug, defining
  `RANVIER_TRACE` for every project (`docs/content/guide/tracing.md` L33-L41). Selective tracing is
  #69. A sample that relies on `Trace.why` runs its explanation checks in a traced build only.
- `Trace.events` copies the full log on each read until #165 lands. A per-turn explanation over a
  long session is O(history) per query; acceptable for a sample, not for production.
- Each graph has one owning thread (`docs/content/concepts/async-graph.md` "Threads and dispatch").
  Many sessions means many owners in one graph, or one graph per session or shard.
- No core change is needed. Neither deliverable is a view, so `view-uses-core.md` does not apply;
  neither compares against Solid, so `framework-comparisons.md` does not apply.

## Recommended scope

Do A, then B. They are independent; A first because it carries no performance risk and B's
transcript model can reuse A's message shape. Close #70 when both land, and leave candidates 3, 5
and 6 to #168, #68 and #65.

### A. `examples/Ranvier.ContextAssembly`

Shape:

- Segment kinds: tool definitions, system text, pinned memory blocks, retrieval results, a todo/plan,
  history messages, compaction summary. Each segment is a projection row keyed by a stable segment
  id, carrying its group, priority, serialised text and token estimate.
- Breakpoint groups in provider order: `tools`, `system`, `messages` (history split at the latest
  cache breakpoint). Each group has a memo over its serialised segments and a prefix-hash memo over
  its own hash and the previous group's.
- Serialisation through `WireCodec` object codecs, so field order is fixed by the codec.
- Token estimate per segment, a `Projection.sumBy` budget, and a selection memo that keeps the
  highest-priority segments that fit. An effect on the budget starts compaction through `createAsync`
  with `CancelPrevious`; compaction folds the oldest history into the summary segment.
- A deterministic synthetic session of at least 30 turns: user messages, tool results, a retrieval
  change, a memory edit, one tool-definition change, one compaction.
- A naive baseline: a pure `assemble : State -> string` that stamps the current turn into the system
  text and serialises tool definitions from a `Dictionary` in insertion order varied per turn.

Acceptance criteria:

1. The project builds in Release and Debug, and is listed in the `examples` group of `build.fsx`
   and in `Ranvier.slnx`; the gate (`dotnet fsi build.fsx -- ...`) builds and tests it.
2. A property test (FsCheck or the repository's existing property framework) generates sequences of
   edits over the segment kinds and asserts: a group's serialised bytes and prefix hash equal those of
   the previous turn whenever no segment in that group or an earlier group changed, and differ
   whenever one did.
3. A property test asserts the graph's assembled prompt equals the output of a from-scratch pure
   assembly of the same state, for every turn of every generated sequence.
4. In a traced build, for every turn of the synthetic session where a prefix hash changes,
   `Trace.why` on that hash memo leads to the write of the segment that changed, and a test asserts the
   segment id it reports. In an untraced build the test is skipped, not failed.
5. Compaction: a test drives the budget over its limit twice within one flight and asserts one
   compaction result is published (the superseded flight's is discarded) and the budget returns under
   the limit.
6. The sample prints a per-turn report: turn, first changed group, predicted cached prefix length in
   estimated tokens, for the graph and for the naive baseline. The README states the totals for the
   synthetic session and labels them predictions from token estimates, not provider measurements.
7. The README opens with what the sample shows and which primitives it uses, and links the provider
   caching rules [4][7].

### B. `stream-session` counter scenarios

Shape:

- A transcript is a keyed projection of messages; each message is a keyed projection of parts; each
  open part is a `createStreamFold` over a `StreamSource` the workload drives. A memo per message
  reads its parts; an effect per message reads that memo through `throttleLast` on the workload's
  `TimedClock`.
- One operation delivers one delta to the newest part and advances the clock past the throttle
  interval.
- Scenario names `stream-session-<messages>` with `<messages>` in 8, 64 and 512. A session-count
  axis (1, 100, 1,000 roots in one graph) is a second family, `stream-sessions-<n>`, each session
  holding 8 messages.
- Variants: `Ranvier (stream session)`, and a baseline `plain (re-concatenate)` that appends the delta
  to a `StringBuilder` per part and rebuilds the message string per delta.

Acceptance criteria:

1. The scenarios run in `bench/Ranvier.Counters` on .NET and Node and appear in the CI counters
   output, with tests in `bench/Ranvier.Counters.Tests` asserting each workload's final transcript
   text equals the concatenated deltas.
2. Retired instructions per operation for `stream-session-512` are within 10 % of `stream-session-8`
   on both runtimes; the docs record the measured ratio whether or not it meets the bound.
3. Per-session cost in `stream-sessions-1000` is within 10 % of `stream-sessions-1` per operation, or
   the docs name the scan that grows.
4. `docs/content/benchmarks/streams.md` gains a `stream-session` section in the format of the
   existing `stream-burst` section.
5. Existing counter scenarios and gates still pass.

If criterion 2 or 3 fails, record the measurement and open a perf issue naming the growing path; do
not change the core inside #70.

## Decisions

Agreed with the user on 2026-10-24.

1. Docs: the sample stays a repository example. `docs/content/guide/examples.md` gains at most a
   one-line link to it, and no dedicated page.
2. Token estimate: characters/4, passed to the sample as an estimator function so a caller can
   substitute a real tokenizer such as `Microsoft.ML.Tokenizers`. Criterion 6 compares the graph and
   the baseline under the same estimator.
3. Many sessions: one graph with one root per session. The README names one graph per session as a
   deployment option.
4. Context inspector: out of scope for #70; it belongs to #168's agent-observable graph.
5. #70 closes when A and B land. Candidates 3, 5 and 6 stay with #168, #68 and #65.
