# Issue #69: traced and untraced primitives in one process

Research note for [#69](https://github.com/shayanhabibi/Ranvier/issues/69), "Myriad source
expansion to expose trimmable non-traced and traced versions of primitives". Repository facts are
checked at `fdfaa4c` (branch `issue/69`, cut from `integration/issues`); paths below are relative to
the repository root. This note builds on the research comment posted on the issue on 2026-10-17
(pinned to `66007fe`) [C1], re-checks it against the current tree, and corrects the parts that
changed since.

## 1. The question

The issue asks for tracing on selected branches of a graph ("reactive subsections dealing with
critical operations like pushing bank transactions"), with replay and a full log, while the rest of
the graph runs at untraced cost. It proposes Myriad to expand one implementation into a traced and
an untraced copy, so that the two never drift.

Two questions sit inside that:

1. **Drift.** Does keeping traced and untraced primitives in lock-step need a code generator?
2. **Mixing.** Can traced and untraced nodes live in one process, and in one graph, with tracing
   paid only by the traced nodes?

## 2. Answer in brief

- Drift is already solved by the compiler. Every trace hook is a `[<Conditional("RANVIER_TRACE")>]`
  static member on `Tracer` (`src/Ranvier/Trace.fs` L777 onward, 64 hooks), so the untraced build
  drops each call with its arguments, and `tools/verify-trace.fsx` (`mergeBaseIlGate`, L938–L960)
  fails a change whose untraced Release IL differs from the merge base, method by method. Myriad
  would replace a compiler feature with a build step and solve nothing new.
- Mixing is blocked by assembly identity and by graph identity, not by drift. `Ranvier` and
  `Ranvier.Traced` hold "the same assembly names, namespaces and version" (`Directory.Build.targets`
  L46–L50; `src/Ranvier/Ranvier.fsproj` L14–L17), and referencing both fails the build
  (`docs/content/guide/tracing.md` L68–L69). Even renamed, two builds are two graphs with no shared
  tracking, flush or batch (section 4.3).
- The design that delivers the issue's goal is **owner-scoped tracing inside `Ranvier.Traced`**: one
  graph, one log, and a per-node "traced" bit that gates each hook. The untraced `Ranvier` package
  stays IL-identical. The work depends on #164 (cost baseline) and #165 (bounded history), and #164
  lists "Introducing selective tracing" as a non-goal, so it lands after them.
- Recommended scope for #69 itself: close the Myriad direction, and file the scoped-tracing design
  as the follow-up with the acceptance criteria in section 6.

## 3. Prior art

### 3.1 Whole-build variants (what Ranvier does today)

- **Solid 2.** `solid-js@2.0.0-rc.18` (the `next` tag, read with `npm view solid-js@next exports` on
  2026-10-24) selects its build through package export conditions: `default` (`dist/solid.js`),
  `development` (`dist/solid.dev.js`) and `observe` (`dist/solid.observe.js`), with server
  equivalents [S1]. Solid picks instrumentation per build, as Ranvier's two packages do. What the
  `observe` build adds was not read for this note (the package contents were not downloaded).
- **MobX.** `spy` "registers a global spy listener that listens to all events", and "in production
  builds, the `spy` API is a no-op as it will be minimized away" [S2]. Instrumentation is global and
  removed from production, as in Ranvier's untraced build.

Neither framework offers a traced subgraph inside an untraced production graph. Ranvier would be
first among the frameworks checked; that is a reason to measure before committing (section 6).

### 3.2 Runtime-gated instrumentation (what scoped tracing would do)

- **.NET `ActivitySource`.** `StartActivity()` "internally determines if there are any listeners
  recording the Activity" and returns `null` when none is, "a performance optimization so that the
  code pattern can still be used in functions that are called frequently"; hot code may also test
  `Activity.IsAllDataRequested` before populating tags [S3]. This is the model for scoped tracing:
  a cheap null or flag test at each instrumentation point, with recording paid only on the scoped
  path.
- **.NET feature switches.** `[FeatureSwitchDefinition]` (.NET 9+) lets the trimmer fold a switch to
  a constant and remove the guarded code; the value is app-wide [S4][S5]. It removes a global
  branch, not a per-node one, and the attribute is absent from `netstandard2.1`, one of Ranvier's two
  targets (`src/Ranvier/Ranvier.fsproj` L4).

### 3.3 Code generation (the issue's proposal)

- **Myriad.** Plugins take "a fragment of AST input" and return AST output printed as source [S6].
  Release facts, from the 2026-10-17 research [C1]: v1.1.0 published 2026-09-24, pinning
  `FSharp.Compiler.Service 43.9.101`, `Fantomas.Core 7.0.5` and SDK `9.0.101` [S7]; Ranvier builds
  with SDK `10.0.100` and `LangVersion latest` (`global.json`; `src/Ranvier/Ranvier.fsproj` L5).
  Expanding the engine means a Fantomas parse and print of `src/Ranvier/Core.fs` (5,607 lines at
  `fdfaa4c`), with the parser one major F# version behind.
- **F# source generators** do not exist: fslang-suggestions #864 has been open since 2020 [S8].
- **`extern alias`**, which C# uses to reference two assemblies with the same type names, has no F#
  equivalent: fslang-suggestions #513 is "approved-in-principle" and open since 2016 [S9].

## 4. How this fits the current core

### 4.1 The traced build is one source compiled twice

- `RanvierTrace=true` appends `RANVIER_TRACE` to `DefineConstants` repo-wide, and Debug defaults to
  traced (`Directory.Build.targets` L7–L19).
- The traced build compiles `TraceEvents.fs`, `TraceSite.fs` and `TraceModel.fs` in addition, and
  carries `AssemblyMetadata("RanvierTrace", "true")` (`src/Ranvier/Ranvier.fsproj` L56–L69, L77–L79).
- Hook call sites at `fdfaa4c` (`grep -c 'Tracer\.'`): `Core.fs` 103, `Projections.fs` 65,
  `Timed.fs` 24, `Streams.fs` 16, `Bindings.fs` 9, `ValueReaders.fs` 1. Traced state sits in
  `#if RANVIER_TRACE` blocks: `Core.fs` 7, `Projections.fs` 2, `Bindings.fs` 2, `Timed.fs` 1.
- Hard rule 1 of the provenance spec: "No existing Release code path gains a branch, allocation or
  call". Hard rule 2: "The traced build runs Release's paths"
  (`docs/.ai/superpowers/specs/2026-09-27-graph-provenance-design.md` L25–L35).

### 4.2 Changes since the 2026-10-17 research

- **The traced build is now AOT-compatible.** `RanvierAotClean` marks the `net10.0` build trimmable
  and AOT-compatible "including when tracing is enabled" (`Directory.Build.targets` L36–L43, from
  #92), and CI publishes the NativeAOT smoke app traced and untraced
  (`docs/content/guide/tracing.md` L421). Scoped tracing in `Ranvier.Traced` therefore keeps
  trimming and NativeAOT.
- **`net8.0` is gone** (#80). Targets are `net10.0` and `netstandard2.1`.
- **Streams carry hooks** (`Streams.fs`, 16 sites, from #100), so a scoped design covers stream memos
  too.
- **No traced benchmark is published yet.** `docs/content/benchmarks/` and
  `docs/.ai/benchmarks/` hold untraced figures only; #164 is the issue that adds traced baselines.

### 4.3 Why two builds do not give a traced subgraph

A read links only into the reading graph's own running computation: `Signal.Value` calls
`graph.Track`, and `Graph.Track` adds the edge when that graph's `current` is set
(`src/Ranvier/Core.fs` L2646–L2650, L2963–L2966). A traced memo reading a signal of another graph
reads it untracked. Two graphs also flush and batch separately, so a bridge effect copying values
across delivers them in a later flush, and a "bank transactions" branch observes intermediate states
(inference from the per-graph flush in `Graph`, `src/Ranvier/Core.fs` L1532 onward).

### 4.4 Where a scope bit would go

- The log is per graph: `GraphNew` creates it on the root owner (`src/Ranvier/Trace.fs` L777–L790),
  and `Graph` reads it through the root (`src/Ranvier/Core.fs` L2031–L2034).
- `Bind` copies the graph's log into every `ObserverSet`, `SourceList` and `Binding`
  (`src/Ranvier/Trace.fs` L795–L813). The set-keyed hooks already return early on a null log:
  `Edge`, `Observer`, `Marked` (L718–L745) and `Write` (L1141–L1158). Skipping `Bind` for an
  untraced node therefore silences those hooks with no further change.
- **47 of the 64 hooks are keyed by the graph, not by a node's set** (first parameter `graph`,
  counted over the `Conditional` members of `Tracer`). These include `Node` (L657–L680, which also
  captures a `TraceSite` per node) and `RunStart` (L1651–L1668); neither tests for a null log. Under a
  scope, a graph-keyed hook needs a membership test on the node id. Node ids come from
  `Graph.NextId`, a dense per-graph counter (`src/Ranvier/Core.fs` L2629–L2632), so the test can be a
  bit array indexed by id held on the `TraceLog`. This was not in the 2026-10-17 research, which
  treated the change as adding null guards.
- `Mark` runs inside the per-observer loop of `ObserverSet.NotifyDirty` (`src/Ranvier/Core.fs`
  L380–L409), so the per-hook test lands on the hottest path of a traced-capable build.
- The traced-only rerun limits (1,000 self-requeues, 100,000 dequeues;
  `docs/content/guide/tracing.md` L45–L47; `RerunGuard`, `src/Ranvier/Trace.fs` L11) must apply to
  traced nodes only, or untraced nodes of a scoped graph diverge from Release behaviour (hard rule 2).

### 4.5 Positioning conflict

The guide's limitations say "Development builds only. A traced build is slower and allocates per
event" and "There is no eviction or checkpoint API" (`docs/content/guide/tracing.md` L375–L378). The
issue's production use contradicts the first statement and needs #165 to fix the second.

## 5. Options

| # | Option | Cost | Benefit | Verdict |
|---|---|---|---|---|
| A | **Myriad plugin** generating traced copies at pack time | Medium–high: plugin, Fantomas round-trip of 5,600-line files on an F# 9-era parser, a second type set users must pick between | Removes drift that the `Conditional` seam and the IL gate already remove; leaves the mixing problem (4.3) unsolved | Reject |
| B | **Second assembly with renamed namespace** (`Ranvier.Traced.dll`, `namespace Ranvier.Traced`) | Medium: source rewrite of `namespace Ranvier` in every file, doubled test matrix, two API copies in a Fable bundle | Both builds load side by side | Reject: two graphs, untracked cross reads, no shared batch |
| C | **Owner-scoped tracing in `Ranvier.Traced`** (a `GraphOptions` tracing mode; nodes under a traced owner get the log and the scope bit) | Low–medium: conditional `Bind`, an id-bit test in 47 graph-keyed hooks, boundary (ingress) events, mixed-graph tests | One graph, one flush, real edges across the boundary; untraced `Ranvier` unchanged; keeps NativeAOT (4.2) | Recommend, after #164 and #165 |
| D | **Runtime switch in untraced `Ranvier`** (feature switch) | Medium; breaks hard rule 1 and the merge-base IL gate; no folding on `netstandard2.1`, Tier-0 or Fable | One package for everyone | Reject unless #164 shows C's guarded hooks cost nothing measurable |
| E | **Type-level tracer** (`Graph<'Tracer>` with a struct no-op) | High: a type parameter on every public type and on the C# façade; Fable erases generics | JIT-specialised zero cost per variant | Reject |
| F | **F# source generators / custom FCS generator** | High; not available upstream [S8] | As A | Reject |

Estimates for option C, from the call sites (unmeasured): a memo recompute crosses roughly 8–12
hooks; at 5–10 instructions per test that is 40–120 instructions against about 545 per chain memo in
the `chain-affinity` counter scenario (`docs/content/benchmarks/memos.md` L42–L50), 7–20 %. Each
traced-capable `ObserverSet`, `SourceList`, `Owner` and `Binding` already carries a log reference and
an id in the traced build (`src/Ranvier/Core.fs` L214–L217 and the other `#if RANVIER_TRACE`
blocks); scoping adds one bit per node id on the log.

## 6. Recommended scope

### 6.1 For #69 (this issue)

1. Record options A, B, D, E and F as rejected with the reasons in section 5, and retitle or close
   #69 against the follow-up below.
2. File the follow-up "feat(trace): owner-scoped tracing in traced builds", depending on #164 and
   #165, with the criteria in 6.2.

### 6.2 Acceptance criteria for the follow-up

An implementer is done when all of these hold:

1. **Untraced build untouched.** `dotnet fsi tools/verify-trace.fsx` passes: untraced `net10.0`
   Release IL equals the merge base method by method, and the public API addition is listed in
   `docs/.ai/public-api-baseline.txt` (or the additions file the script reads).
2. **Default unchanged.** `GraphOptions` gains a tracing mode with `All` (today's behaviour) as the
   default. Under `All`, the traced test suite (`dotnet fsi build.fsx -- test` on a `RanvierTrace=true` build) and the
   byte-identical dump check pass with no fixture change.
3. **Scope API.** Under `Scoped`, nodes created under an owner marked traced (by `Trace.scope` or a
   `createRoot` option; the untraced build keeps a `Conditional` or inline stub, as `Trace.named`
   does in `src/Ranvier/TraceApi.fs`) record events; every other node records none. A test asserts
   that a `Scoped` graph with no traced owner holds only its `GraphNew` event.
4. **Gate in every hook.** Each graph-keyed hook in `Tracer` tests the node's scope bit before any
   allocation, including `TraceSite.capture` in `Node`; set-keyed hooks rely on the unbound null
   log. The `verify-trace.fsx` hook-site lint is extended to reject a graph-keyed hook without the
   test.
5. **Ingress events.** When an untraced source marks or is read by a traced node, the traced node's
   log records an ingress event naming the source id and the value read. `Trace.why` on a traced
   memo fed by an untraced signal ends at that ingress event.
6. **Atomicity.** A `batch` that writes an untraced signal and a traced signal produces one flush,
   and the traced memo reading both never observes one write without the other (test).
7. **Release behaviour for untraced nodes.** An untraced node in a `Scoped` graph never raises the
   rerun guard (test that requeues an untraced node past `RerunGuard.Limit`).
8. **Replay of a scope.** Folding a scoped log with `TraceModel` reproduces the traced nodes' values,
   using ingress events as the inputs (test over a mixed graph).
9. **Fable.** The traced Fable test run (`dotnet fsi build.fsx -- test-fable`) passes with the
   mixed-graph tests included, and `docs/.ai/fable-compat.md` lists no new failure.
10. **Cost recorded against #164.** The #164 counter scenarios run on three builds: untraced,
    traced `All`, and traced `Scoped` with no traced owner. The report under
    `docs/.ai/benchmarks/counters/` gives instr/op and bytes/op for each. `Scoped` with no traced
    owner stays within the budget #164 sets (proposed: 10 % instr/op over untraced, 0 extra
    bytes/op).
11. **Docs.** `docs/content/guide/tracing.md` documents the mode, the boundary semantics and the
    cost, and the "Development builds only" limitation is reworded to match the user's decision on
    question 7.1.

## 7. Open questions for the user

1. **Production positioning.** Is `Ranvier.Traced` meant for production use on scoped branches? The
   guide says "Development builds only" today; option C only pays off if that changes.
2. **Milestone.** #164 lists selective tracing as a non-goal, and #165 is a prerequisite for
   bounded retention. Should #69 leave the 1.0.0-rc milestone in favour of a follow-up after #165?
3. **Scope marker.** Per owner (`createRoot` option / `Trace.scope`), or per node (`Trace.label`
   style)? Per owner matches disposal and is cheaper to test; per node is finer-grained.
4. **Boundary payloads.** Ingress events retain the value read. For a payment branch that is the
   point; for large values it is a retention cost. Should ingress capture go through #166's payload
   codecs, with a lossy marker for values without a codec?
5. **Budget.** Is 10 % instr/op for a `Scoped` graph with no traced owner the right ceiling, or
   should `Scoped` be required to match `All` minus recording?
