# Issue #66: core MCP tooling, scoped by the #168 evidence

Status: research note, 2026-10-25. Branch `issue/66`, cut from `integration/issues` at `aae54f2e`. The #168 spike is
read from `origin/issue/168` (PR #187, open, base `integration/issues`). The 2026-10-17 exploration comment on #66
[C1] is the starting point; this note re-checks it against the spike and the experiment the user accepted as #168's
evaluation [R1].

## 1. Question

#66 asks for three things [I1]:

1. **Core MCP**: "full access to sources, and reads of memos and/or push values" of a graph.
2. **Creation of graphs**: hooks that build graphs from scripts or F# quotations, aimed at "self-improving/learning
   contexts in a harness".
3. **Elmish MCP**: writes limited to an Elmish dispatch loop.

The #168 spike has since built a version of items 1 and 3, and an experiment measured whether it helps an agent. The
question is therefore narrower: **given that the spike exists and showed no measurable benefit on a small sample,
what does #66 build, what does it defer, and what measurement decides the next step?**

## 2. Summary

- The spike already delivers the low-cost part of #66: snapshot resources, a `dispatch` tool over a typed message
  decoder, `wait_version`, and traced provenance tools (`why`, `why_not`, `waiting_on`, `trace_state`,
  `trace_lookup`) on a dedicated graph thread [R2]. The one core change the exploration asked for, a public awaitable
  dispatch, is in core as `Graph.DispatchAsync` (`src/Ranvier/Core.fs` L2191, L2203).
- The experiment: 20 runs, every run in both workflows succeeded in one repair iteration; the MCP workflow cost about
  twice the tokens in round 1 and 47% more in round 2 at the median, with more tool calls and more wall clock [R1].
  The baseline already included SageFs. On a two-file sample with a failing property test, the tools replaced a read
  the agent made anyway.
- The cost direction matches published guidance: tool definitions and intermediate results occupy context on every
  turn [P1], and tool work should be judged by evaluation tasks that collect accuracy, tool calls, tokens and runtime
  [P2].
- **Recommendation: build no more MCP surface in #66 until a discriminating evaluation shows a benefit.** Scope #66
  as (A) an evaluation harness with tasks of the three kinds the experiment named, (B) two fixes the experiment
  surfaced that improve tracing for every client, MCP or not, and (C) a decision rule that says which deferred item
  is built once the harness reports. Graph creation from scripts or quotations, raw signal writes, Fable/WebMCP and
  packaging `Ranvier.Mcp` are deferred or dropped (section 6).
- #66 needs no change to `src/Ranvier`'s public API, so it does not block the 1.0.0-rc API freeze. Its `core` label
  and milestone are open questions (section 8).

## 3. Prior art

| Source | What it says | Bearing on #66 |
|---|---|---|
| Anthropic, "Code execution with MCP" (2025-11-04) [P1] | Tool descriptions "occupy more context window space, increasing response time and costs"; every intermediate result passes through the model; moving tool use into code cut one workflow from 150,000 to 2,000 tokens. | Explains the experiment's token overhead: each MCP turn returns JSON documents the agent already had a cheaper route to. Favours small, targeted tool outputs and code-side composition (FSI) over more tools. |
| Anthropic, "Writing effective tools for agents" (2025-09-11) [P2] | Build dozens of evaluation tasks from realistic use, each with a verifiable outcome; collect accuracy, tool-call and task runtime, tool calls, tokens and tool errors; use held-out tasks. | The method for criterion A. One sample with one defect class is too few tasks to separate workflows. |
| SWE-bench (Jimenez et al., arXiv:2310.06770) [P3] | Repository-scale repair tasks drawn from real issues, judged by tests the agent does not see. | Model for task construction: real-sized codebases, hidden verdict tests, no failing test handed to the agent. |
| Chrome DevTools MCP [P4] | Runtime inspection (DOM, network, performance traces) for coding agents. | Prior art for the case the experiment named: symptoms visible only in the running application. Its value is runtime state with no source equivalent; Ranvier's trace tools are closest to that in the traced build. |
| SageFs [P5] | An F# REPL over MCP in a separate daemon; agents already evaluate code against a loaded project. | Covers "creation of graphs from scripts" today, and is the third arm of the evaluation: the same `Trace` API called from FSI, without a Ranvier MCP server. |
| MCP 2026-07-28 [P6][P7] | Stateless protocol; `subscriptions/listen` replaces `resources/subscribe`; tools are "arbitrary code execution" to be gated on user consent. | The spike pins `2025-11-25` (finding 4 in [R1]); serving `subscriptions/listen` is deferred work, not #66's first step. |

## 5. What the evidence does and does not show

- **Shows:** with source access, a failing property test and two short files, the MCP tools add overhead and remove
  no step. All 20 runs named the cause; the trace tools gave a correct and direct account in every experimental run
  that used them [R1].
- **Does not show:** anything about codebases too large to read, defects with no failing test, or symptoms visible
  only at runtime. Those are untested, not refuted [R1].
- **Measurement gaps in #168's protocol:** one defect class per round; runs reached MCP through a CLI bridge rather
  than native client tools; time to symptom and time to cause were not separated (finding 3); the FSI arm (the same
  `Trace` calls from SageFs, no Ranvier server) was not run, so the experiment cannot say whether any benefit belongs
  to MCP or to the trace API.

## 7. Recommended scope and acceptance criteria

#66 lands on `issue/66` as three parts. Nothing in `src/Ranvier`'s public API changes.

### A. Evaluation harness (decides everything deferred)

1. **Subject.** A sample application of at least 3,000 lines across at least 15 F# files, built on `Mvu` with
   derived memos, a keyed collection (`createProjection`), an async source and a timed operator, served by
   `Ranvier.Mcp`. It lives under `examples/` and carries its own expectation checks under `tests/`, hidden from the
   runs.
2. **Tasks.** At least six seeded defects, two of each kind:
   - *non-local*: cause in a different file from the symptom (for example a comparer or an untracked read in a helper);
   - *no failing test*: the runs get no test that fails on the defect;
   - *runtime-only*: the symptom needs a message sequence of length 5 or more, or an async or timed interleaving.
   Each task has a prompt stating the observable rule, and a hidden verdict test.
3. **Arms.** Baseline (source, build, tests, SageFs); MCP (baseline plus the sample's `Ranvier.Mcp` server registered
   as a native MCP server, not a bridge); FSI-trace (baseline plus a documented SageFs recipe that calls `Trace.why`,
   `whyNot` and `state` on the running graph, no Ranvier server).
4. **Runs.** At least five runs per task per arm, each in a blinded copy with a fresh history and only the task
   prompt (the isolation of [R1] round 2). Every run is reported, failures included.
5. **Metrics per run.** Verdict (hidden test), tool calls, tokens (input, output, cache), wall clock, repair
   iterations, time to first correct statement of the symptom, time to first correct statement of the cause.
6. **Report.** `docs/.ai/research/<date>-issue-66-evaluation.md` with per-task medians and paired ratios against the
   baseline, with a bootstrap 95% interval per task kind.

### B. Tracing fixes the experiment surfaced

1. **B1.** `TraceSite.capture` skips every frame whose assembly carries a Ranvier library marker (an
   `AssemblyMetadata` key, or the existing name list extended to `Ranvier.Elmish`, `Ranvier.Mcp`, `Ranvier.View*`,
   `Ranvier.Query`, `Ranvier.Wire`). A traced test creates nodes through `GraphHost.Start` and `Mvu`, and asserts
   that each node's identity path names the test's own file. `tools/verify-trace.fsx` passes (the untraced build is
   unchanged, since `capture` returns null there, `TraceSite.fs` L7).
2. **B2.** `Exposure` accepts a provenance scope: `Exposed` (opt-in) or `WholeGraph` (the default, today's
   behaviour). Under `Exposed`, `trace_state` lists only exposed nodes, `trace_lookup` rejects other paths with a tool
   error, and a `why` chain renders unexposed steps as `{ "id": n }` without labels or values. Tests in
   `McpTraceTests.fs` cover each tool under both scopes; `docs/content/guide/mcp.md` states the boundary.
3. Both run in the full gate (`build.fsx -- test`, traced Mcp stage, `test-fable` where Fable code changes).

### C. Decision rule, recorded before the harness runs

For each task kind, the MCP arm **benefits** when its median tokens or wall clock is at most 0.8x the baseline's with
the 95% interval below 1.0, and its success rate is no lower. Then:

- MCP benefits on any kind: file follow-ups for C2 (packaging and AOT), then C1 if a benefiting task needed push
  updates, then C3 if a benefiting task turned on a record field.
- FSI-trace benefits and MCP does not: invest in the FSI recipe and `Trace.render` output instead; keep
  `Ranvier.Mcp` experimental.
- Neither benefits: keep `Ranvier.Mcp` as an unpacked example, close #66, and record the result in the guide.
- Intervals that straddle 0.8 or 1.0 are reported as inconclusive for that kind; the rule applies to the conclusive
  kinds only.

#66 closes when A's report and B's fixes land and the rule's outcome is recorded in `docs/.ai/PRIORITIES.md`.

## 8. Open questions for the user

1. **Milestone and label.** #66 changes no public API in `src/Ranvier`. Move it out of 1.0.0-rc (due 2026-10-31) and
   drop the `core` label?
2. **Harness cost.** Part A is about 90 agent runs per pass (6 tasks, 3 arms, 5 runs). Accept that budget, or start
   with the three non-local and runtime-only tasks?
3. **Native MCP in runs.** #168's runs used a bridge because workflow agents cannot register an MCP server. Can the
   harness run agents with a registered server, or is the bridge accepted as the MCP arm?
4. **B2 default.** Should `Exposed` become the default scope, changing the spike's current `WholeGraph` behaviour
   before #187 merges?
5. **B1 location.** B1 changes `src/Ranvier/TraceSite.fs`, a traced-only file. Land it under #66, or as a #166
   follow-up?

## 9. Decisions (2026-10-25)

The user answered the questions in section 8:

1. **Milestone and label:** #66 moves to the "Agent-observable reactive core" milestone and drops the `core` label.
2. **Harness cost:** start with a preliminary pass much smaller than the 3-task subset: one task whose defect is
   non-local or visible only in the running application, three arms, three runs each (9 runs). Run the 45-run pass over
   the three non-local and runtime-only tasks only if the preliminary pass leaves the question open. In the user's
   words: "Reduce cost for preliminary. Defer full 45 runs to if not resolved in less."
3. **MCP arm:** native MCP sessions, not the CLI bridge. Each MCP run is a separate session with the sample registered
   as a stdio server in its `.mcp.json`.
4. **Trace scope (B2):** add an opt-in `Exposed` scope; `WholeGraph` stays the default.
5. **B1:** a follow-up to #166, filed as #193 in 1.0.0-rc.
