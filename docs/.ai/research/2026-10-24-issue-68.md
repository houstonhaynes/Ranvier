# Issue #68: persistent graph state and storage adapters

Date: 2026-10-24. Branch `issue/68`, base `integration/issues`. Ranvier code is cited at `fdfaa4c3` (paths relative to
the repository root). Prior-art sources are the primary sources listed in the issue's exploration (accessed
2026-10-17); their numbers below match the issue's source list. This note re-checks every Ranvier claim in the issue
against the current tree and records what has changed since `66007fe`.

## Question

How should a Ranvier application keep its state across a process restart, a page reload or a server failover, and
which storage adapters should ship "out of the box"? Concretely:

1. Which parts of a graph are durable state, and which rebuild from code?
2. What gives a persisted node an identity that survives a restart?
3. Which codec and store interfaces does the package expose, and how do writes leave the graph thread?
4. What is in scope for the 1.0.0-rc milestone (due 2026-10-31), and what is deferred?

## Summary

- Persist inputs (signals, keyed collections, the `Mvu` model) under application-chosen keys. Derived nodes recompute
  from restored inputs. This matches redux-persist, Jotai `atomWithStorage` and Orleans grain state [29][32][34].
- The codec question is settled in-tree since the issue was written: `Ranvier.Wire` (#109, commit `8eb33e0a`) is an
  AOT-clean JSON codec with one wire text on .NET and Fable, over a vendored Thoth.Json, and the NativeAOT smoke app
  already exercises it. Persistence uses `WireCodec<'T>` and needs no serialiser choice of its own.
- The core has no public "flush settled" hook. A persisted input can be observed with `createEffectOn`; one write-behind
  drain per flush needs either a per-graph coalescer in the persistence package built on the graph's dispatcher, or a
  small core hook. The recommendation is to build it on existing primitives first and raise a core hook only if the
  per-flush coalescing criterion fails.
- Recommended 1.0.0-rc scope: a `Ranvier.Persistence` package with keyed persisted inputs, a store interface, an
  in-memory store, a file store (.NET) and a `localStorage` store (Fable). Query-cache persistence and database adapters
  follow; persisted memo caches, whole-graph snapshots and persisted dependency graphs are out of scope.

## How it fits the current core

- **Identity.** `NextId` asserts the graph thread and increments a counter (`src/Ranvier/Core.fs:2629-2632`). Trace
  identity paths come from labels, sites and creation order, and the tracing guide states labels are names, not keys
  [6][7]. A persisted node takes an explicit string key.
- **Construction.** `Signal<'T>` stores `initial` as its value at construction (`src/Ranvier/Core.fs:2920-2925`).
  A persisted signal reads its stored value synchronously from a preloaded set, so the first read already returns it.
- **Observation.** `createEffectOn compute act` (`src/Ranvier/Api.fs:310-312`) runs `act` on each settled value unequal
  to the last. An effect per persisted signal or model reads the value and marks its key dirty. This is the core
  primitive for change detection; the persistence package keeps only the dirty-key set and the outbound queue, which
  have no core equivalent.
- **Flush boundary.** `Graph.Flush` drains the effect queue and calls `Tracer.FlushEnd` in its `finally`
  (`src/Ranvier/Core.fs:2341-2381`). The tracer hook is traced-only and internal. Untraced code has no public callback
  after a flush. A coalescer that posts one drain through `graph.Dispatcher` when the first key turns dirty, and encodes
  the dirty set when that drain runs, yields one `SaveMany` per flush on a dispatcher that drains after the current
  flush (inference: holds for `SynchronizationContextDispatcher`, `src/Ranvier/PlatformDispatcher.fs:17-21`; an
  immediate dispatcher drains on the calling thread, so coalescing there needs a batch or a core hook).
- **Thread hand-off.** Encoding runs on the graph thread (the value is immutable by contract for keyed rows and Elmish
  models, but encoding there removes the question). Store IO runs off the graph thread. Loading back onto a live graph
  after construction needs a graph-thread dispatch with result propagation; `Graph.DispatchApplied` exists but is
  internal (`src/Ranvier/Core.fs:2089`), and #167 proposes the public `DispatchAsync`. The preload design avoids that
  dependency for the first release.
- **Unowned signals.** A signal created in a re-running body restarts from its initial value on each run [14]. A
  persisted signal belongs at the root or in a keyed factory; the package documents this and the analyzer package
  (`tools/Ranvier.Analyzers`, #154) may later flag it.
- **Query.** `QuerySnapshot` separates `Data` from `FetchStatus` and keeps data on refresh failure
  (`src/Ranvier.Query/Types.fs:116-123`), so a hydrated entry maps to "data present, stale". `Define` has no name
  (`src/Ranvier.Query/Queries.fs:307`), which blocks persistence until a named overload exists.

## Prior art (primary sources, numbered as in the issue)

- **Keyed named state.** redux-persist persists a reducer tree under a key and runs ordered migrations above the
  stored version [29][30]. Jotai `atomWithStorage` reads lazily unless `getOnInit` is set [32]. Orleans loads grain
  state before activation and writes explicitly with `WriteStateAsync`, with ETag conflicts [34].
- **Query caches.** TanStack Query's `persistQueryClient` restores a dehydrated cache, discards it by `maxAge` and
  `buster`, and throttles saves to at most once a second [33].
- **Write-behind.** Oracle Coherence coalesces repeated changes within the write-behind interval and stores them in one
  `storeAll` call [36].
- **Store durability.** Redis AOF `everysec` can lose one second [37]; SQLite WAL lets readers run alongside a writer,
  and `synchronous=NORMAL` gives up durability on power loss [39]; Postgres `ON CONFLICT DO UPDATE` is an atomic upsert
  [38]; `localStorage` is synchronous and blocks the page [40].
- **Persisted derivations.** rustc persists results keyed by stable fingerprints [25]; Bazel keys results by action
  hash [27]; Nominal Adapton names computations for reuse across runs [26]; Salsa's disk persistence is still an open
  issue [22]. Each needs stable names or fingerprints for every node, which Ranvier closures lack.
- **Whole-tree snapshots.** MobX-state-tree snapshots a tree that is pure data [31]; a Ranvier graph also holds
  closures, owners and flights.

## Recommended scope (1.0.0-rc)

Option 1 only, as a new package `src/Ranvier.Persistence` (`net10.0;netstandard2.1`, `RanvierAotClean`, Fable-compatible),
referencing `Ranvier` and `Ranvier.Wire`.

### Core and view state

- **Core primitives used:** `Signal<'T>` (the persisted value), `createEffectOn` (change detection per persisted input),
  `KeyedCollection` with `NewValueReader` and `KeyChange` (row-level changes), `Mvu` `init` (model hydration),
  `onCleanup` / `Owner` (detaching a persisted input), `graph.Dispatcher` (scheduling the drain).
- **Package-owned state:** the preloaded record set, the dirty-key set, the outbound save queue and its completion task.
  The core holds no IO state, so these stay in the package. No view code is involved.

### API sketch

```fsharp
type StoredRecord = { Key: string; Version: int; Payload: string }

type IStateStore =
    abstract LoadMany: keys: string list -> Task<StoredRecord list>
    abstract SaveMany: records: StoredRecord list -> Task
    abstract DeleteMany: keys: string list -> Task

type Versioned<'T> = { Version: int; Codec: WireCodec<'T>; Migrations: (int * (string -> string)) list }

module Persist =
    val loadAsync: store: IStateStore -> keys: string list -> Task<PersistSession>
    val signal: session: PersistSession -> key: string -> codec: Versioned<'T> -> fallback: 'T -> Signal<'T>
    val collection: session: PersistSession -> key: string -> codec: Versioned<'V> -> keyOf: ('V -> 'K) -> KeyedCollection<'K, 'V>
    val mvu: session: PersistSession -> key: string -> codec: Versioned<'Model> -> init: 'Model -> update: ... -> Mvu<'Model, 'Msg>
    // PersistSession.FlushAsync: unit -> Task   completes when every save queued so far has finished
```

Payloads are `string` (wire text), which suits `localStorage` and file stores directly.

### Acceptance criteria

- **A. Zero cost when unused.** The counter bench shows no instruction or allocation change for graphs with no
  persisted nodes; the bench reports the per-write cost of a persisted signal.
- **B. Coalescing.** A batch writing N persisted signals produces exactly one `SaveMany` with N records; writing the same
  key twice in one batch saves it once. Tested on the default dispatcher and on a `SynchronizationContextDispatcher`. If
  either fails, stop and raise option 1a with the user before adding a core hook.
- **C. Round trip.** A test writes persisted inputs, calls `FlushAsync`, builds a fresh graph from a new `loadAsync`
  over the same file store, and reads equal input values, with derived memos equal to those of an uninterrupted run.
  The first read of a persisted signal returns the stored value (no fallback-then-stored transition observed by an
  effect).
- **D. Versioning.** An older stored version runs its migrations in order; a newer one fails `loadAsync` with a typed
  error naming the key; a `Decode` `Error` follows the session's policy (fail, or discard and use the fallback); a
  store-wide buster mismatch discards every record.
- **E. Collections.** Editing one row of a persisted keyed collection saves that row only (row store) or one document
  (document store), and a restored collection keeps insertion order.
- **F. Platforms.** The NativeAOT smoke app publishes with a persisted signal and no trim or AOT warnings; a Fable test
  round-trips a record and a union through the `localStorage` store with Wire codecs.
- **G. Durability point.** `FlushAsync` completes only after the store's `SaveMany` task for every earlier write has
  completed, and faults with that task's exception.
- **H. Docs.** A guide page states that persisted inputs belong at the root or in a keyed factory, that derived nodes
  recompute, and that the trace dump is not a persistence format.

### Deferred

- Option 2 after option 1 lands (needs a named `Define` overload; acceptance: a restored family reports
  `Data = Some _` and `IsStale = true` before any IO, `Ensure` starts a refresh, and `maxAge` or buster mismatch starts
  empty).
- Option 3 adapters after the interface is stable, each passing a shared conformance suite with an ETag conflict test.
- Option 4 until a #70 workload needs it. Options 5 and 6 are not pursued.
- Relation to #65: share `IStateStore` and the versioned-record shape; a #68 snapshot can be the checkpoint for an
  event stream after #165's checkpointed truncation. #68 never requires the traced build.

4. If criterion B fails on some dispatcher, is a public untraced after-flush hook in the core acceptable (option 1a)?

6. Multi-process writers: ship last-writer-wins in the first release, with ETag support left to the database adapters?
