# Reactive core comparison: Ripple source review

The probe scripts this note runs were removed from the branch; they are at commit [d784929](https://github.com/shayanhabibi/Ranvier/tree/d784929cd9c67eed51bb319d1f3c2b993dcd9b54).

Researched 2026-10-02. Ripple baseline: published `Fable.Ripple 1.0.0-beta.6`, repository commit `83e49254be753343b1dd3838df58e83dd39cdeb1`. Ranvier baseline: the current repository and its documented Fable differences. This review concerns the reactive core; renderer breadth and DOM event/mount failures are excluded. It combines an independent source review with the parent investigation's measured fixtures; evidence types are identified below.

## Advantages actively sought for Ripple

**Per-node equality is a substantive flexibility advantage.** `Var.createWith`, `Signal.computedWith`, `mapWith` and `map2With` accept individual cutoff functions. Two same-typed values can therefore have different equality rules without separate graphs. Default equality is structural, with an explicit reference comparer available. Ranvier documents graph-wide equality policies and excludes individual node comparers. Neither structural nor identity equality is universally better: structural comparison avoids equal-copy updates but can traverse large values. [Ripple API](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Api.fs), [Ranvier equality](../content/guide/equality.md).

**A smaller, convenient synchronous API is an ergonomic advantage for simple applications.** Writable Vars implement the same read-only Signal interface consumed by derivations. `map`, `map2`, `map3`, `bind`, a `signal` computation expression, and disposable subscriptions are readily available. There is no graph activation step for ordinary usage. This is a convenience judgment, not evidence that Ranvier cannot express the same computation. Ranvier's `createEffect` returns unit, but `new Effect(graph, body)` supplies individual disposal and inspection. [Ripple types](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Types.fs), [builder](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Builder.fs), [Ranvier effects](../content/guide/effects.md).

**Its packaging is more immediately usable for Fable consumers.** Ripple publishes a separate core package without a DOM dependency. Live NuGet metadata shows Ranvier is published for .NET through `0.1.0-preview.3`; the parent investigation downloaded that package and found DLLs for net10.0, net8.0 and netstandard2.1, but no `.fs` or `.fsproj` source payload for Fable compilation. The Fable publication gap remains; the local Fable page's claim that neither target has a package is stale. This is Fable distribution readiness, not proof of long-term stability: Ripple is beta and its recent changelog includes a breaking interface change. [Ripple project](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Fable.Ripple.fsproj), [changelog](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/CHANGELOG.md), [Ranvier live package index](https://api.nuget.org/v3-flatcontainer/ranvier/index.json), [preview.3 package](https://api.nuget.org/v3-flatcontainer/ranvier/0.1.0-preview.3/ranvier.0.1.0-preview.3.nupkg), [local Fable status](../content/fable/index.md).

**Bundle size is a measured advantage for the existing graph fixture.** The narrower graph exports measured 19,442 bytes for Ripple versus 48,236 for Ranvier, minified. These are retained fixture outputs, not minimum engine footprints; Ripple's adapter also imports its DOM package. Larger renderer-fixture size comparisons must not be relabelled bare-core comparisons. Node memory/allocation superiority is unmeasured. Ripple's inline first-edge representation and stable dependency-prefix reuse are credible optimization choices, but inspecting them does not establish an advantage against Ranvier. [Existing size investigation](benchmarks/ripple/2026-10-02-comparison.md), [Ripple node layout](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/ReactiveNode.fs).

**Independent model lifetimes favor Ripple in a new core-only experiment.** The parent investigation ran two Chromium experiments, each with five warmups and 25 alternating-order samples, checking aggregate final-value and effect-run-count checksums. For 10,000 creations of an independent diamond model, one write, reads and disposal, median times were Ranvier 7.8 / Ripple 6.2 ms in run 1 and 8.7 / 7.2 ms in run 2: Ripple took approximately 17–21% less time. Ranvier creates a fresh Graph per model; Ripple opens a root on its global engine. This measures those context choices, not multiple roots sharing one persistent Ranvier graph, allocation counts, or steady-state propagation. [Run 1](https://github.com/shayanhabibi/Ranvier/blob/d784929cd9c67eed51bb319d1f3c2b993dcd9b54/docs/.ai/benchmarks/ripple/2026-10-02-core-lifetimes-run-1.json), [run 2](https://github.com/shayanhabibi/Ranvier/blob/d784929cd9c67eed51bb319d1f3c2b993dcd9b54/docs/.ai/benchmarks/ripple/2026-10-02-core-lifetimes-run-2.json), [runner](https://github.com/shayanhabibi/Ranvier/blob/d784929cd9c67eed51bb319d1f3c2b993dcd9b54/docs/.ai/benchmarks/ripple/2026-10-02-core-lifetimes.mjs). Copy the runner into the extracted comparison probe, build that fixture using its existing reproduction script, then run it from the probe directory with RTK. It starts and stops its own preview server; port 5181 must be free. The timed loop performs no DOM operations. Timing includes the reads and checksum accumulation.

## Shared synchronous capabilities and semantic choices

Both support lazy cached derivations, dynamically tracked dependencies, shared memo results, synchronous effects, batching, untracked reads and equality cutoff. These should not be credited uniquely to either side. Ripple's computed nodes are pulled on demand rather than queued; observed ones refresh through the effects that read them. Its first-party tests exercise diamonds and dynamic rewiring. [Ripple derived values](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/docs/content/ripple/derived.md), [Ripple tests](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/tests/Fable.Ripple/Signal.fs), [Ranvier memos](../content/guide/memos.md).

Ripple `Peek()` refreshes a stale computed without tracking; Ranvier `Peek` returns its stored value and does not refresh it. Ranvier `untrack(fun () -> memo.Value)` gives the former behavior. Current-read convenience versus stored-snapshot access is a semantic tradeoff, not missing reactivity. Within a batch, Ripple setters still mark dependencies and reads pull current values; effects defer to outer batch exit. Ranvier documents the same current memo-read/deferred-effect distinction. [Ripple implementation](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Types.fs), [Ranvier batch](../content/guide/batch.md).

## Advantages supported for Ranvier

**Per-run ownership and cleanup.** Ranvier effects, owning memos and boundaries dispose children and run cleanups before rerunning. Pure memos explicitly reject ownership creation. Ripple's scope is established by `Signal.root` during its synchronous factory; recomputation does not create or reactivate an effect-owned scope. Thus its `onCleanup` means scope teardown, not automatic previous-run cleanup. This is source inspection, not a newly executed subscription probe. Application-managed scopes can implement replacement lifetimes, but that is additional code rather than the same built-in contract. [Ripple scope](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Scope.fs), [tracking](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Tracking.fs), [Ranvier cleanup](../content/guide/cleanup.md).

**Error resilience and graph state.** Ranvier records effect errors while allowing later effects to run, continues cleanup after individual cleanup failures, and supplies graph-level pending/failed states and boundaries. Ripple's scheduler lets exceptions escape and clears its queue. The existing browser test demonstrated that a throwing effect left a healthy sibling stale on later updates: this is a core finding, unlike DOM listener findings. Ripple root factories also restore ambient scope in `finally` without disposing a failed factory's scope; teardown has no per-callback catch. The latter conclusions are source-derived until independently exercised as core-only probes. [Ripple scheduler](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/src/Fable.Ripple/Internal/Scheduler.fs), [existing tested findings](benchmarks/ripple/2026-10-02-comparison.md), [Ranvier contracts](../content/concepts/contracts.md).

**A broader state-graph toolkit.** Owned async values with flight policies, cancellation signals, automatic pending/error propagation, selectors, keyed projections, lookups and incremental collection views are documented Ranvier capabilities. The complete pinned Ripple core API is primarily sources/computeds/effects/scopes; its async demo manages loading/error state and request generations in application code. Ripple's DOM list reconciliation is a different layer and cannot substitute for reactive-core collection primitives. [Ranvier async graph](../content/concepts/async-graph.md), [collections](../content/guide/collections.fsx), [Ripple async baseline](RESEARCH-fable-ripple-comparison.md).

**Diagnostics and independent graphs.** Ranvier provides node status/run/error inspection and optional causal graph tracing, while Ripple exposes observer counts. Explicit graph instances also support independent queues and equality configurations; .NET adds affinity guards and dispatchers. Those thread facilities offer cross-platform reuse, not an advantage in a single browser thread. Ripple's tests explicitly identify a single global, single-threaded engine. Its core targets netstandard2.1 and inspected code is ordinary F#: this review does not establish that it cannot execute on .NET. [Ranvier tracing](../content/guide/tracing.md), [threading](../content/guide/threading.md), [Fable limitations](../content/fable/index.md), [Ripple test context](https://github.com/fable-hub/Fable.Ripple/blob/83e49254be753343b1dd3838df58e83dd39cdeb1/tests/Fable.Ripple/Signal.fs).

**One measured propagation speed advantage, with a narrow scope.** Two prior runs gave Ranvier 10.7–10.9 ms versus Ripple 15.1 ms for 100,000 diamond graph writes. That establishes the result of one particular fixture, not a general throughput ranking. Ripple's measured independent-model lifetime advantage above points in the other direction for a different workload. Async roundtrip timings were similar; those include transport/state/DOM instrumentation and are not pure async-core timings. Neither propagation nor lifetime result establishes an overall winner. [Measurements and methodology](benchmarks/ripple/2026-10-02-comparison.md).

## Limits

This source-review agent performed no new runtime probes; its parent supplied the two independent-model measurements above. Cycle behavior, large fan-out, deep graphs, allocation/retention, high-churn dynamic dependencies and equality-heavy workloads remain unmeasured. Inspection of Ripple's recompute path finds no explicit evaluating/cycle sentinel, but this alone does not justify an untested cycle-failure claim or a Ranvier cycle-safety claim. Both projects remain prerelease; download availability, source size, test count and renderer breadth do not establish production maturity.
