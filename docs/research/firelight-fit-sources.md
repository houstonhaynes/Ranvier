# Firelight integration evidence

Checked 2026-10-05. Firelight `main` resolved through GitHub's commits API to `1ea8aefe67fb3e1cffa218785aa3edfc26c849fe`. Links below pin that revision. This note uses documentation and workflow metadata; it does not claim an F# semantic audit or a measured Ranvier integration.

## Existing capabilities

- [Signals package](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/site/content/packages/signals.md): Firelight already binds `@lit-labs/signals`. Signals can live outside the DOM and be shared between independent components. Computed values are lazy and cached. Registered components track reads during rendering. Signal-aware templates update individual bindings. The underlying TC39 proposal and Lit Labs package remain experimental.
- [Signals translation guide](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/site/content/from-lit/signals.md): `LitSignals.defineElement` applies Lit's signal watcher at registration, because F# cannot express the mixin as its base class. `LitSignals.html` watches signal values inserted directly into holes; reading a value with `get` during rendering instead watches the component. `watch` can watch one hole with ordinary Lit HTML. `updateEffect` has automatic disconnect cleanup. The low-level `Signal.subtle` API and general `withWatch` are not bound.
- [Elmish package](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/site/content/packages/elmish.md): `ElmishController` hosts an immutable-model, pure-update loop in a component. Each model drives rendering. It supports commands and a full Elmish program, including subscriptions and tracing. Existing users therefore already have structured state transitions and testable domain logic.
- [Task package](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/site/content/packages/task.md): `LitTask` supplies initial/pending/complete/error states, reruns when its argument array changes, ignores obsolete completion, and supplies a browser `AbortSignal` to cancel requests. This is meaningful existing async support. Shared keyed caching, deduplication across components and mutation coordination are not promises made by this page; their absence from documentation alone is not proof of absence from all code.
- [Architecture](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/docs/components-and-templates.md): components own lifecycle, state and a shadow root; templates are plain stateless view functions. The recommended default is templates, promoting to components for actual lifecycle/state/encapsulation needs. Communication uses properties, events and context. Ranvier should support those boundaries rather than require every view fragment to become a custom element.

## Integration seam and constraints

[Controllers guide](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/site/content/guides/controllers.md) documents `ReactiveControllerBase`, host registration, connect/disconnect hooks and `host.requestUpdate`. This is a natural proposed seam for a Ranvier adapter: subscribe on connect, dispose on disconnect, invalidate Lit when selected graph values change. Reconnect must reestablish subscriptions and reconcile current state. A host update is component-level invalidation; it does not itself create Lit's per-template-part watchers. Lifecycle cleanup, setup-before-registration and avoiding controllers created inside `render` are explicit Firelight concerns.

[Prerendering guide](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/site/content/guides/prerendering.md) documents Node-based Lit SSR and hydration. Module initialization, constructors and render execute during prerendering; controller hooks do not. Browser-only work belongs in connect/later hooks, and first browser rendering must match prerendered state. A proposed adapter must keep graph creation safe in Node and avoid effects or async-state changes that spoil initial hydration. Ranvier does not automatically solve those requirements.

## Author priorities and validation

[Firelight's own comparison](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/site/content/why.md) explicitly positions it as Lit-shaped bindings whose output imports Lit directly. A minimal counter measured on 2026-10-03 was 6,006 gzipped bytes, versus 5,929 for the TypeScript Lit version. These are narrow baseline measurements, not a Ranvier comparison. They make additional runtime/bundle cost relevant to the author. The page acknowledges pre-1.0 API changes, a young ecosystem and string-template limitations.

[Testing recipe](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/site/content/cookbook/testing.md) recommends pure F# tests for domain logic and Playwright for rendered behavior. [Site checks](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/.github/workflows/site.yml) builds demos with size budgets, compiles doc snippets, exercises pages in Chromium and runs Kanban E2E. [Sample tests](https://github.com/roboz0r/Firelight/blob/1ea8aefe67fb3e1cffa218785aa3edfc26c849fe/.github/workflows/samples.yml) run Kanban unit tests on .NET and router tests in Fable/Node plus .NET. An adapter needs browser lifecycle and hydration checks, not just graph-unit tests.

## Assessment, explicitly an inference

Ranvier has a plausible role as an optional application-state or shared server-state layer. Its case must rest on a demonstrated capability beyond Firelight's existing signals, Elmish controller and task controller, such as reusable domain graphs across .NET/browser code, selected model slices or coordinated cache/mutation behavior. Replacing Firelight's default signal runtime merely to obtain signals/computed values duplicates existing features and can lose template-part integration. A separate optional package or application-level controller protects Firelight's Lit correspondence and minimal core, while permitting a focused experiment. No speed, size or reliability superiority has been established here.

For the Firelight maintainer, this creates another dependency, lifetime contract, compatibility matrix, documentation path and source of support questions. An optional adapter can let Ranvier's maintainers own those costs while preserving Firelight's close correspondence to Lit's documentation. For an application author, retaining pure MVU updates while selecting reactive slices or sharing domain graphs with .NET is attractive; learning graph ownership, disposal and scheduling alongside Lit and Elmish is a cost. Small component-local counters and single requests already have simpler Firelight-native solutions.
