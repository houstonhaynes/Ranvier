# Xantham customization as a Ranvier DOM generator

Assessed 2026-10-08. Recommendation: use Xantham as the typed browser-surface input to a Ranvier-owned generator. Its supported customization API can generate property companions today, but it does not directly express a complete Ranvier constructor, event, attribute, lifecycle and SSR API.

## What the supported API actually exposes

The [customization guide](https://github.com/shayanhabibi/Xantham/blob/4216cac45554e9ac66bd5242f819952f0317df3b/site/content/xantham-cli/guide/customization.md) documents F# extension registration through `Pipeline.generateWith` and `runWith`. CLI and JSON configuration do not load extension assemblies. Each callback sees the original immutable semantic snapshot.

The [public signature](https://github.com/shayanhabibi/Xantham/blob/4216cac45554e9ac66bd5242f819952f0317df3b/src/Xantham.Generator/Customization/Contract.fsi) exposes four output operations: add attributes, emit companions, replace property interop, and replace owned declarations. Semantic queries provide source types, canonical package/path selection, explicit heritage, implemented types, members, resolved property types, original JavaScript keys, readonly and optional flags, declaring identities and output targets. Opaque handles and `BindingType.display` are the public seam; this is not a public arbitrary-AST emitter or a complete structured property-type inspection API.

Companions produce marker interfaces plus extension properties. Inherited substitutions and readonly accessors are preserved. The [companion renderer](https://github.com/shayanhabibi/Xantham/blob/4216cac45554e9ac66bd5242f819952f0317df3b/src/Xantham.Generator/Customization/Output.fs) fixes the generated shape: `[<Interface>]` marker, `[<AutoOpen>]` extension module, and either erased stubs or direct Emit getters/setters against the original object key. It rejects empty companions, invalid or colliding names, dependency cycles and foreign/non-property members. There is no constructor, View builder, listener or arbitrary new declaration operation in that contract.

The escape hatch can emit complete F# source through `Replacement.raw`, replacing an owned non-generic interface. It must preserve a declared export contract and pass `generateValidatedWith`/.NET compilation. Raw replacements are excluded from producer catalogs; replacements that alter a contract with heritage consumers are rejected. This makes raw replacement a possible experiment, not a clean general-purpose scaffold backend. These restrictions and ownership/provenance behavior are documented in the [replacement and provenance sections](https://github.com/shayanhabibi/Xantham/blob/4216cac45554e9ac66bd5242f819952f0317df3b/site/content/xantham-cli/guide/customization.md#replace-a-declaration-explicitly).

## Author's view

The valuable part is avoiding a hand-maintained copy of the browser type hierarchy. Canonical selection, inherited generic substitutions, JavaScript key preservation and deterministic companion provenance are substantial foundations. A Ranvier adapter can own its vocabulary and generate a small, consistent facade while ordinary browser bindings retain their source identity.

Upstream's [design](https://github.com/shayanhabibi/Xantham/blob/4216cac45554e9ac66bd5242f819952f0317df3b/docs/.ai/plans/2026-10-06-generator-customization-design.md) explicitly assigns framework conventions to the extension author and excludes event DSLs, comprehensive DOM-to-JSX policy, arbitrary F# AST construction and discovery of every DOM declaration. That scope fits the proposal if Ranvier accepts ownership of those missing semantics. It argues against asking Xantham to become a Ranvier runtime compiler.

## Sceptic's view

Browser DOM properties describe an already existing object. Ranvier's future reusable View must describe work performed on mount, without constructing DOM during View construction. Direct property Emit access does not automatically provide deferred updates, equality policy, subscription disposal, event options, typed `currentTarget`, attribute serialization or server rendering. Erased companions are meaningful only when a framework plugin interprets them. Neither mode alone satisfies that runtime contract.

The upstream [Partas acceptance harness](https://github.com/shayanhabibi/Xantham/blob/4216cac45554e9ac66bd5242f819952f0317df3b/tests/Xantham.Generator.PartasGate/README.md) establishes an intended executable check for a small selected property surface and Partas's own plugin. It is evidence of an appropriate validation strategy, not evidence that every DOM member works in Ranvier. In particular, tag constructors, listeners, SSR behavior and Ranvier policy remain to be proven.

TypeScript DOM metadata supplies types, not attribute/property semantics. A generator still needs explicit policy for boolean attributes, live versus default form state, property-only members, URL/namespace behavior, readonly rejection and browser-only state. Event handler properties are not automatically the listener API Ranvier should expose. `event.target` must retain its general/nullable type; a typed registration element belongs on `currentTarget` or an explicit wrapper, not an unchecked target cast. These are design inferences for Ranvier, not verified Xantham features.

## Recommended pipeline and acceptance slice

The [revised pipeline](xantham-ranvier-dom-evaluation.md#proposed-pipeline) supersedes the sequence below. Prefer a catalogue-aware minimal emitter if the identity bridge is proven; retain the generator/projection path when it avoids duplicating authentication or type mapping. A catalogue supplies binding identity and provenance, not the full DOM member model or Ranvier runtime policy.

Pin `Xantham.Generator`, support packages, TypeScript compiler and source/catalog inputs. Use a dedicated generator executable, select an explicit DOM entry surface, and fail on missing or ambiguous metadata. Preserve ordinary Xantham bindings. Emit Ranvier property companions only where their fixed shape is useful; have a separate Ranvier emitter consume a normalized metadata snapshot and a curated policy map to produce constructors, updates and event helpers. The current public snapshot may need a small structured export/enrichment seam for tag maps, event maps and resolved type shapes; do not build that contract by parsing generated F# or internal records.

Start with `div`, `input`, `button`, one boolean attribute, `value`/`defaultValue`, one event and one namespace-sensitive element. Acceptance must compile the generated API and execute repeated mounts, updates, listener removal and disposal; confirm construction allocates no DOM; verify SSR output separately; reject readonly assignment; and regenerate twice with identical source/manifest hashes. These are proposed gates, not completed checks.

The decision is therefore conditional approval of the typed-generation direction, with a deliberately small proof before replacing the DOM facade. The likely authoring gain is broad, consistent type coverage. No runtime performance improvement follows merely from adopting this generation pipeline.

## Minimal upstream opening: clarification

The absence of an arbitrary declaration emission operation does not mean output inspection is unavailable. Public [Model.fs](https://github.com/shayanhabibi/Xantham/blob/4216cac45554e9ac66bd5242f819952f0317df3b/src/Xantham.Generator/Model.fs) already exposes `FsTypeRef`, `FsDecl`, `FsMember` and `RenderModel.Decls`/`Files`. `Pipeline.generateWith` returns that model. Ranvier can inspect the shipped declaration IR and write its own additional source files without adding an upstream output hook. This route requires relevant tag/event maps to be reached and shipped; the rendered IR has less source identity, inherited metadata and provenance than the semantic projection. An additive `BindingType.inspect`, canonical named-type lookup and final-qualified type renderer would improve the supported semantic seam without exposing mutable pipeline internals. Existing `BindingType.display` prints the stored type without the final producer/reference qualification used by the companion renderer.
