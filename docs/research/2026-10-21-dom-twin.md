## Named exceptions to gates 1 and 3

The production baseline for completion of #159 explicitly includes the head-placement fix and the core inspection
API below. Gate 1 compares `bundle-production.json`; gate 3 applies the exact patches listed in
`production-changes.json` to pristine master output before comparing it with the branch. Historical `bundle-base.json`
and `bundle-i1.json` are retained, not overwritten or described as passing against the current toolchain.

- **Head entry placement failures (Phase 4 review I1).** `MountState.HeadIn` routes a failure of
  `DocumentHead.activate` to the root's `Hold` or the scope's `FailAll`, as a placed hook's failure goes. The one
  generated file that changes is `src/Ranvier.View.Dom/Mounting.js` (`experiments/Ranvier.View.Foundation/Mounting.js` before the view graduated): three more `Placement` imports, the
  summary's last sentence, and a `try`/`catch` around `activate`. Each minified bundle grows by 0.06–0.07 kB raw and
  0.03–0.04 kB gzip (`explicit` 215.31 → 215.37 kB, gzip 62.88 → 62.91 kB; `combined` 220.98 → 221.05 kB, gzip
  63.92 → 63.96 kB, measured before the graduation; after it, every entry is 45 B larger than master 433da79, e.g.
  `explicit` 214077 → 214122 B and `combined` 219748 → 219793 B). `2026-10-21-dom-twin/bundle-i1.json` retains the historical hashes recorded with this fix;
  gate 3 reads `2026-10-21-dom-twin/i1-mounting.diff` and accepts exactly its two body changes (imports remain ignored).
  `generated-tests-base` must contain the unmodified merge-base output. A baseline already holding the fix, an
  ambiguous hunk, or any additional body change fails, even if `--allow` matches `Mounting.js`. The hunk can be
  selected explicitly with `--expected-hunk <file>` when checking another baseline.

- **Non-evaluating core status.** `Status.Stale` reports a dirty computation without reading or recomputing its value.
  The status getters in `Core`, `Bindings`, `Projections`, `Streams`, and `Timed` combine this bit with their existing
  status. `createEffectNode` exposes an effect's existing `INode` inspection surface. These are additive public API
  changes from `1ea136e3`, not inspection-code elimination. The six `production-*.diff` files accept exactly those
  getter/API changes and the generated Core initialization-field line-number change. The inspection registry and
  dump implementation must still be absent without `RANVIER_VIEW_INSPECT`.

The scoped baseline decision retains these APIs, which the non-evaluating dump uses, as part of #159 rather than
removing their functionality to recover an obsolete hash. It does not relax a performance threshold or allow any
other shipping body change. The complete primitive instruction comparison on the final PR revision remains a merge

## The departures seam on .NET

`Departures.seam` is one object for the process on .NET, as the JavaScript module's object is for a page. A
registration on any thread turns `Enabled` or `ReflowEnabled` on for every later mount on every thread, and nothing
turns them off. Twin tests that need a clean seam use `Departures.createSeam ()`.

## The two harnesses

Both harnesses give a case the same environment:

- **The document.** The twin gives each case a fresh document. The jsdom runner keeps one jsdom for the run and empties
  its head and body, clears their attributes and blurs the active element before each case. One document serves the
  run, as one serves a page: Foundation keeps a definition's compiled template on the definition, so a template
  compiled in a closed window's document would reach later cases with that window's prototypes. Listeners a case adds
  to `document` or `window` stay for later jsdom cases.
- **The clock.** `conformance-host.mjs` replaces jsdom's `queueMicrotask`, `setTimeout`, `clearTimeout`,
  `requestAnimationFrame` and `cancelAnimationFrame` with the twin clock's semantics: the view's queued microtasks and
  `Post` share one queue that only `RunMicrotasks` drains, and `AdvanceBy` runs due timers and 16 ms animation frames in
  due order, draining the queue after each callback. `Date` follows the clock. Promise reactions still run natively
  under jsdom.
- **Listener failures.** jsdom's "Not implemented" notices (form submission, navigation) are left out of
  `ListenerErrors`; the twin has no counterpart.
- **Interception.** `Intercept` wraps a DOM method of one node, or of every node when the target is null: jsdom
  patches the instance or the node prototypes, and the twin's bridge consults a per-document table before its member
  table. The twin's host adds and removes the view's listeners through `addEventListener` and `removeEventListener`,
  as the JavaScript does, so an interception sees them.

The delegation cases run the .NET port of the delegated walk on the twin: nested keyed mounts, `stopPropagation`,
inner and outer hosts, a native stop between target and host, a detached host, non-bubbling direct listeners, and,
through interception, shared, moved and self-disposing hosts. The range, template and delegation cases include no
head entries and no hydration, so the `keepHead` copy path and the hydration rollback snapshots run first with the
document and hydration cases.

## Dump values and JSON

The dump inspects F# record fields and tuples on .NET, and record data properties under Fable. Other class values
are opaque: their type name is shown without invoking their property getters. A core node used as an instance is
also opaque. Core nodes held in record fields use the node's `Peek` and `Status` inspection contract.

Value kinds follow the representations shared by both targets. Fable erases `char` and `Guid` to strings and
ordinary integer and floating-point types to numbers, so those kinds are `string` and `number`. Arrays and
`ResizeArray` values use `array`; anonymous records use `record`. An `int64` keeps its exact integer text, decimal
keeps its decimal text, unions show their case and fields, and maps and sets show their count. Options show their
contained value. The `values` fixture pins these choices on both hosts.

`ranvier-view-dump/1` has keys `schema`, `mount`, `root`, and `head` in that order. `mount` is null for a host capture,
or an object with `prefix`, `phase`, `commits`, and integer `failures`. Root entries have a `kind` discriminator and
the fields of their `DumpNode` case. Attributes and properties are arrays of name/value pairs; property strings
are raw values, without display quoting or truncation. Instance field `value` remains bounded display text, with
its `kind` and `status` alongside it. Node ids and trace paths are emitted only with `NodeIds` enabled. A list row
with a held exit is captured as a keyed `LeavingRow` (JSON kind `leaving` with `key`); held exits are excluded from
the live-row count in the text form.

Every dump fixture records text and JSON from the same capture. The .NET fixture runner checks JSON fields against
the captured tree, and the host comparison checks both representations byte-for-byte. Captures retain their text
options, so `Debug.text` uses the limits supplied to `Debug.capture`.

### Bridge cost estimate

The twin runner measures the proxy path and the underlying bridge implementation separately for five common
members. Each pair is warmed for 100 calls, then measured in ten batches of 1,000 calls, alternating which path
runs first. Raw proxy, direct and difference samples are retained in `cases-twin.json`. A separate, untimed mount
temporarily wraps the private node dispatch entries to count calls, then restores them in `finally`. Those
wrappers are absent from the mount/reorder/hydration timings and from product code.

| Member | Calls during mount | Lower-median proxy minus direct |
|---|---:|---:|
| `firstChild` | 1,008 | 548.5 ns/call |
| `nodeType` | 2,005 | 409.0 ns/call |
| `cloneNode` | 1,001 | 2,952.8 ns/call |
| `appendChild` | 1,000 | 756.4 ns/call |
| `data` setter | 1,000 | 2,641.8 ns/call |

These members account for 6,014 of 6,050 intercepted **node-bridge** calls (99.405%). Multiplying their individual
lower-median differences by those counts gives 7.727 ms, or **70.8%** of the 10.915 ms warm mount median. This is a
microbenchmark-weighted estimate, not a measured whole-case profile. It uses representative element/text inputs
and includes argument conversion, wrapping and allocation as well as dispatch. Other node members and other
bridge interfaces are omitted; collection operations and the rest of the renderer are not separately attributed.
Tiering, allocation and cache effects can differ between the microbenchmarks and a real mount.

The estimate exceeds decision 1's quarter-of-case investigation threshold. It supports a separate generated-bridge
investigation in Phase 7, with a direct implementation comparison before choosing an approach. It does not establish
that generated classes would recover 70.8% of the mount time, or require that follow-on implementation in this PR.
