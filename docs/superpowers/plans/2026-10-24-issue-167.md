## Current state (2026-10-24)

- `Graph.Dispatch(work: Action)` (`src/Ranvier/Core.fs`) calls `Graph.Post`: inline when `IsOnGraphThread`, otherwise enqueue on the inbox and `dispatcher.Post (Action this.PumpFromDispatcher)`. Under Fable `Post` runs the work inline.
- `Graph.Drain` runs inbox items FIFO; a throwing item goes to `root.RecordError` and the rest still run; the drain ends with `RequestFlush` when it ran anything.
- `Graph.DispatchApplied(work: unit -> unit) : Task` is internal, used by `FlightPolicy.Queue` (`publishQueued`). Its task completes whether or not the work threw and carries no result: the gap the issue names.
- `Graph.Dispose` disposes `root` and runs no inbox work; items queued before disposal still run on the next drain.
- `ManualDispatcher` (the default with no synchronisation context) leaves the inbox for `Graph.Pump`; `SynchronizationContextDispatcher` posts the drain to the context; `ImmediateDispatcher` drains on the posting thread (raising under `Guarded` off-thread).

## Design

### API shape

Members on `Graph`, following `Graph.Dispatch(work: Action)`: a BCL delegate parameter so C# and F# lambdas both convert, and a `CancellationToken` overload in the BCL style.

```fsharp
member DispatchAsync : work: Func<'T> -> Task<'T>
member DispatchAsync : work: Func<'T> * cancellationToken: CancellationToken -> Task<'T>
```

No `Api.fs` function: `Dispatch` has none either, and the graph receiver is explicit because an external caller has no ambient graph. A `Task` (non-generic) overload is left out: `Func<unit>` covers it from F#, and C# callers return a value or use `Dispatch`. Recorded so a later request for a `Func<Task>`/`Action` overload is a deliberate addition.

### Semantics (the documented contract)

- **Context.** The work runs where `Dispatch` work runs: inline when the caller is on the graph thread (inside the graph under `Serialised`), otherwise from the inbox on the drain the dispatcher schedules.
- **Completion.** The task completes after the work returns, with its result; it faults with the exception the work threw, unwrapped (`task.Exception.InnerException` is the original object, and `await` rethrows it). A faulting `DispatchAsync` item is not recorded in `Root.Errors`: the caller receives it.
- **Effects.** Completion marks execution of the work, not the end of what it triggers. Effects woken by its writes run as they do for `Dispatch` work: at the write, or at the end of a batch the work opens, before the task completes. An inline call inside an enclosing batch completes its task first, and that batch's flush runs the effects. Async memos and flights it starts settle later. The doc comment says so.
- **Continuations.** On .NET the task is created with `RunContinuationsAsynchronously`, so an awaiter never resumes inside the drain, on the graph thread or while holding a `Serialised` graph.
- **Owner thread.** Inline on the graph thread: the work runs before `DispatchAsync` returns, and the task is already completed or faulted. Awaiting it there cannot deadlock. Blocking on `.Result` of an off-thread `DispatchAsync` from the owning thread does deadlock when only that thread drains; the doc comment says so.
- **Ordering.** `DispatchAsync` items share the inbox with `Dispatch`, settles and flight completions: FIFO by enqueue, from one thread. Inline calls run at the call.
- **Disposal.** A call on a disposed graph (`Root.IsDisposed`) returns a task faulted with `ObjectDisposedException` and does not run the work. `Graph.Dispose` faults the task of every `DispatchAsync` item still in the inbox the same way, with no drain needed, and a later drain skips the work. An off-thread call that races disposal is registered before it (and faulted by it) or refused at the call. Plain `Dispatch` keeps its current behaviour.
- **Cancellation.** A token cancelled before the work starts cancels the task and the work does not run; an already-cancelled token returns a cancelled task without enqueueing. Once the work starts, it runs to completion and the token is ignored (graph work is synchronous). A token cancelled while the item waits cancels the task at once. Cancellation does not remove the item from the inbox; the drain skips it.
- **Undrained inbox.** Under `ManualDispatcher` the task completes only when the owning thread calls `Pump`. Documented, not changed.
- **Dispatcher failure.** Under `Guarded` with `ImmediateDispatcher`, an off-thread call raises from `DispatchAsync` as `Dispatch` does, and the item stays queued; its task completes on the next drain. Unchanged semantics.
- **Fable.** `Post` runs inline; the task is a resolved or rejected promise from `Platform.completion`. Cancellation token overload compiles under Fable (the token is checked before running).
