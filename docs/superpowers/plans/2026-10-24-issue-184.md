# Issue #184: Input journal and replay for untraced and traced builds

Branch `issue/184`, cut from `integration/issues` at `dd8bff65` (#166 merged). Split from #65 by
`docs/.ai/research/2026-10-24-issue-65.md` (on `issue/65`), option A, section 6.1, with the user's
answers in its section 8.

## Goal

An input journal that records a graph's external inputs in both builds, and a replay driver that
reproduces a run (diagnostic replay) or re-enacts it (re-enactment), without the traced build's cost.

## Acceptance criteria (copied from the issue)

1. A cart-sample test journals `Mvu` messages and external signal writes, replays them in diagnostic
   mode into a fresh traced graph, and the replayed final `Trace.snapshot` and the `Trace.why` output
   of every effect run equal the live traced run's.
2. A property test: for any sequence of external writes, settles and failures, replaying the journal
   into a fresh untraced graph yields the same values for every keyed input and every memo.
3. Re-enactment mode re-runs async work; a test shows a changed async result flows through replay.
4. Writes made by a running computation are not journaled; a test asserts it. An unregistered payload
   produces an entry marked non-replayable, and `replay` fails with a named error on it.
5. [x] With `Journal = None`, paired counters (`bench/Ranvier.Counters`, interleaved in one run) show the
   untraced `signal` and `memo` steady-state scenarios within the noise interval of the baseline; the
   only IL difference reported by `tools/verify-trace.fsx` is the guarded hook, listed in the PR.
6. [x] Snapshot plus tail: restoring a #68 snapshot taken at a journal position and replaying the later
   entries equals an uninterrupted run (once #68's format exists).
7. [x] Fable: the replay test passes under `build.fsx -- test-fable`. User-facing docs cover the journal,
   both replay modes and restore.

**User ruling (2026-10-24):** criterion 6 depends on #68's stored-state format, which has no implement
issue yet. Every other criterion is built; criterion 6 is recorded as waiting on #68 in the PR body
and the PRIORITIES log. No snapshot format is invented here. The docs' restore section states the
contract the journal offers #68 (entry `Seq` is the journal position) and that restore lands with #68.

## Core and view state

This is core work (`src/Ranvier`, both builds) plus `src/Ranvier.Elmish`. No `Ranvier.View` code
changes.

**Core primitives used:**

- `Graph` and its dispatcher (`Graph.Dispatch`, `RequestFlush`, the flush pass): replay applies each
  entry on the graph thread and flushes at each journaled flush boundary, so replay schedules work
  exactly as the live run did.
- `Signal<'T>` setter and `AsyncSource<'T>.Settle` / `Fail`: the input sites the hook observes.
- The graph's running-computation state: tells an external write from a derived one.
- `Mvu` `Dispatch` / `Apply`: the message site.
- `Trace.snapshot` / `Trace.why` (traced build): the oracle for criterion 1.

**View-owned state:** none.

## Design

### Types (in `Types.fs`, before `GraphOptions`; functions in a new `src/Ranvier/Journal.fs` after `Api.fs`, both builds)

```fsharp
type JournalEntryKind = Write | Settle | Fail | Message | Flush

type JournalPayload =
    | Empty                                              // Flush
    | Encoded of codec: string * version: int * data: string
    | NonReplayable of payloadType: string               // unkeyed node, or no codec

type JournalEntry =
    { Schema: int            // 1
      Stream: string         // IInputJournal.Stream
      Seq: int               // 1-based, per graph; the journal position #68's snapshot records
      Kind: JournalEntryKind
      Key: string option     // the application key; None for an unkeyed node and for Flush
      PayloadType: string    // the CLR / Fable type name of the value
      Payload: JournalPayload }

type IInputJournal =
    abstract Stream: string
    abstract Record: entry: JournalEntry -> unit
```

`GraphOptions.Journal: IInputJournal option`, default `None`, with `WithJournal` matching the
existing `With*` members, and a fifth line in `ToString` (AotSmoke text updated).

### Keys and codecs

- `JournalCodec<'T> = { Name: string; Version: int; Encode: 'T -> string; Decode: string -> Result<'T, string> }`,
  a record of functions as `TraceCodec` is. Core keeps no `Ranvier.Wire` reference; a `WireCodec<'T>`
  plugs in as `{ Name = ..; Version = ..; Encode = wire.Encode; Decode = wire.Decode >> Result.mapError string }`,
  shown in the docs and used by the tests (the test projects reference both).
- `Journal.key (key: string) (codec: JournalCodec<'T>) (signal: Signal<'T>) : Signal<'T>` and the
  `AsyncSource<'T>` overload register the node on its graph's journal and return it. A no-op when the
  graph's `Journal` is `None`. A duplicate key on one graph raises `ArgumentException` naming it.
- **Key space:** the key is an application string, the key #68's `StoredRecord` will use, so #166's
  stable node key and #68's application key are one key space. It is a separate API from the trace
  `Named` path because the journal must work in the untraced build, where trace paths do not exist.
  In the traced build `Journal.key` also writes the key as the node's trace label when the node has
  none, so a traced dump shows the same name.

### Recording

- The graph resolves `options.Journal` once into a nullable internal field (`journal`), plus a
  bindings table `Dictionary<int, JournalBinding>` and a seq counter, allocated only when a journal is
  present.
- **Hook sites** (the only untraced IL change; each is one field load and a null check):
  1. `Signal<'T>.Value` setter, before the equality cutoff (an equal write is still recorded, since
     the traced log records it too and replay must reproduce its seq).
  2. `AsyncSource<'T>.Settle` and `Fail`, inside the posted body, so the entry order is the
     graph-thread order.
  3. The end of a flush pass, recording a `Flush` entry when any entry was recorded since the previous
     boundary. Replay flushes at each boundary, so batching matches the live run.
- **Derived inputs are skipped:** a write or message made while a computation runs (memo, effect,
  async-memo body, including under `untrack`) is not recorded; nor are writes made inside a journaled
  `Mvu` message's `Apply` and its synchronous commands. The check uses the graph's run state, not
  `current`, because `untrack` clears `current`.
- `WriteExcept` is only called by a running computation, so it carries no hook.
- An unkeyed node, or a keyed node whose `Encode` raises, records `NonReplayable payloadType`; the
  entry is never dropped.

### Mvu

`Mvu.journal (key: string) (codec: JournalCodec<'Msg>) (mvu: Mvu<'Model, 'Msg>)` registers the
message site. `Dispatch` from outside a computation records a `Message` entry before `Apply`, then
runs `Apply` and the synchronous commands with recording suppressed (the root write and the commands'
writes are derived from the message). A later message dispatched by an async command is a new
external message and is recorded. Ranvier.Elmish reaches the hook through `InternalsVisibleTo` from
`Ranvier` if the assembly already grants it, and otherwise through a public
`Journal.registerSite` / `Journal.recordMessage` / `Journal.derived` set that any adapter can use.

### Replay

```fsharp
type ReplayMode = Diagnostic | Reenact
type JournalReplayException(seq: int, key: string option, reason: string) = inherit exn
Journal.replay (mode: ReplayMode) (graph: Graph) (entries: JournalEntry seq) : unit
Journal.replaying (graph: Graph) : ReplayMode option
```

- Runs on the graph thread (same contract as a signal write; off-thread callers use `Graph.Dispatch`),
  applies entries in `Seq` order, and calls the graph's flush at each `Flush` entry.
- `Write` decodes through the key's codec and writes the signal; `Message` decodes and dispatches
  the `Mvu`; `Settle` / `Fail` settle or fail the source in `Diagnostic` mode and are skipped in
  `Reenact`, where the application's async work runs again (gateways read `Journal.replaying` to skip
  external calls in `Diagnostic` mode).
- Fails with `JournalReplayException`, naming the seq, key and payload type, on a `NonReplayable`
  entry, a key not registered on the target graph, a codec name or version mismatch, or a decode
  error. `Fail` entries carry the exception's type and message as the payload, and replay raises a
  `JournalReplayedFailure` (message preserved) into the source.
- `MemoryJournal(stream)` is the in-memory `IInputJournal` (an `Entries` list) for tests and samples.

### Scope decisions

- **Async memos are not journal sites.** The research note's site table lists `AsyncSource` settles as
  the async input; an async memo's flight is a computation over journaled inputs. Diagnostic replay
  of a graph whose async memos call external services re-runs them unless the application routes the
  result through a keyed `AsyncSource` (documented). Substituting async-memo flights is a follow-up.
- **No JSON form in this issue.** Entries are F# records; a JSONL writer belongs with the #65 export
  sink or #68.
- **Seq is the journal position.** #68's snapshot will record a `Seq`; replaying entries with a greater
  `Seq` after restore is the tail. Criterion 6 waits on #68 (user ruling).

## Decisions

- **Application key, not trace path.** The trace `Named` path does not exist untraced; the journal
  needs a key in both builds, and it must be #68's key. `Journal.key` takes the string and mirrors it
  into the trace label when traced.
- **Codec as a record of functions.** Matches `TraceCodec`; keeps `src/Ranvier` free of a
  `Ranvier.Wire` reference (the two packages pin different `System.Text.Json` versions). A
  `WireCodec<'T>` adapts in one expression.
- **Flush boundaries are journaled.** Without them a replay cannot reproduce batching, and the
  traced `why` output of criterion 1 would differ.
- **Equal writes are journaled.** The traced log records them; skipping them would shift trace seqs.
- **Criterion 6 deferred to #68** by user ruling.
- **Replay batching.** A one-entry segment replays unbatched, and a `Flush` entry flushes only when the
  segment left the flush owed, so a traced replay adds no batch or flush events the live run lacked.
- **Cart codecs.** `Ranvier.Tests` has no `Ranvier.Wire` reference, so the cart test uses hand-written
  text codecs; the guide shows the Wire adapter.
- **Budget run (step 11).** `tools/verify-trace.fsx` and `build.fsx -- perf build` add git worktrees,
  and the counter A/B harness reads Linux thread counters, so the lane ran the same comparisons by
  hand against a `git archive` export of `aae54f2e`: `docs/.ai/benchmarks/journal/README.md`.
  Instruction counts need an elevated shell and are not collected.
- **Exactly-once replay of async-produced inputs (review of PR #188, user ruling).** Each entry carries
  an `Origin`: `External`, or `Produced` for an input of attributed async work. The journal attributes
  an `Mvu` command's dispatch (each command list shares one `JournalWork`) and any input passed to
  `Journal.produce` with work captured by `Journal.work`. `Reenact` skips `Produced` entries and the
  re-run work makes them; `Diagnostic` applies them, and `produce` drops the inputs of work captured
  before the diagnostic replay returns (the recorder's generation is marked covered for the replay,
  then renewed). No application code reads `Journal.replaying` for correctness. The entry `Schema`
  is 2. Attribution is explicit rather than an `AsyncLocal`, so it behaves the same under Fable and
  adds nothing to a computation's run; an effect's continuation write that bypasses `produce` stays
  `External`, as the guide states. Two `Message` entries with no `Flush` between them (an unobserved
  model) replay in one batch, which adds batch events to a traced replay; the Mvu tests observe the
  model.
- **Work numbers replace the covered generation (second review of PR #188).** `Produced` carries the
  number of its work, counted per graph in start order: `Journal.work`, each `Mvu` command list, and
  each effect run (`Effect` body and `EffectOn` action) take the next number on both platforms, so a
  graph built and driven by the same code numbers its work alike. A `Diagnostic` replay counts the
  replayed `Produced` entries per work and drops a re-run input only while its work has an unmatched
  count; a command in flight when the journal was cut, and work started on the target before the
  replay, stay live. A failing replay withdraws the counts of its unapplied entries. Dropping happens at
  each input site (write, settle, failure, message), so `produce` still runs its closure. `Reenact`
  skips only `Produced` entries and applies external settles and failures. On .NET the effect run's
  number flows into its continuations through an `AsyncLocal`, set only on a graph with a journal, and
  `Graph.Dispatch` from a continuation keeps it; this supersedes the earlier choice of explicit-only
  attribution, since the review required the core to attribute the async-source settle path. Fable has
  no async context, so its effect and async-memo continuations need `Journal.produce`; the guide and the
  Fable page say so. `Journal.work` now asserts the graph thread, as its counter is graph state.
- **Replay-relative work identity (third review of PR #188).** The graph-global work number made a
  re-run work's number depend on everything the target ran first (an extra effect, an earlier
  commanded message, an earlier replay), so inputs doubled or unrelated live inputs dropped.
  `Produced (started, index)` now names the work by the `Seq` of the last non-`Flush` entry recorded
  before it and its position after that entry. A `Diagnostic` replay names the work it re-runs in the
  replayed entries' `Seq` values and counts expectations per replay, so earlier work and earlier replays
  on the target never match; setup work (`started = 0`) matches by position from construction, and a
  replay of producing setup work requires a target with no recorded entry (seventh review). A derived input passed through `produce` (a re-run command
  whose await completed synchronously) is matched too. An entry the replay applies records its origin
  in the target's own `Seq` values. `Drain` clears the journal ambient, so an unattributed inbox item
  drained under another work's execution context records `External`.
- **Matching by call (fourth review of PR #188).** Counting a work's expected entries let a synchronous
  dispatch the live run left unrecorded (`dispatch Loading; await; dispatch Loaded`) use up the
  expectation of the work's later recorded input: `Diagnostic` gave `[1; 2; 2]` for `[1; 0; 2]`.
  `Produced (started, index, call)` now also numbers the input's call within the work: each `produce`
  call or command dispatch that made an input, recorded or not, and each direct input of an effect's
  continuation. A re-run input is dropped only while an entry of the same work and call is unmatched,
  so the unrecorded synchronous dispatch is live and an await that completes synchronously only on the
  replay still matches its recorded call.
- **Matching target (fifth review of PR #188, user ruling option A).** Setup work is keyed by its
  position among the works started before the graph's first entry, so a target that started an
  unrelated effect first replayed an initial command's async message twice (`[2; 5; 5]`). Replay
  now requires a matching target and detects a mismatch; setup work is not re-keyed by identity
  (option B) and attributed inputs are not dropped (option C). A graph that started work before its
  first input records a `Setup` entry with `Seq` 0 ahead of that input (codec `setup` version 1): the
  works in start order, `effect` or `work`, each followed by the quoted key it was named after
  (`Journal.name`; `Mvu.journal` names its initial commands' work). Before applying any entry,
  `Journal.replay` in either mode raises `JournalReplayException` on the `Setup` entry, naming the
  recorded and the found setup work, unless the target's setup work begins with the recorded setup
  work; work started after the recorded setup work leaves the target matching. Entries with no
  `Setup` entry match every target. The entry schema is 3. The synchronous part of an `Mvu` command,
  including an initial command of `Mvu.withCmd`, runs in a derived section (`Journal.derived`), so an
  initial command's synchronous dispatch no longer records a non-replayable unkeyed `Write`.
- **Equal setup descriptions (sixth review of PR #188).** An unnamed effect or `Journal.work`
  describes as its kind alone, so a target that started an extra unnamed work ahead of an equal
  setup work passed the prefix check, and the extra work took the setup work's `Produced` entries
  (the reviewer's `[work]` against `[work, work]` gave 21 for 11). `Journal.replay` now also raises
  when a setup work that made a recorded input embeds in the target's setup work at a later
  position too; the reason names `Journal.name` as the way to tell the works apart. A setup work
  with no recorded input may repeat, so an extra effect ahead of an effect that only reads stays
  matching. The limit, recorded in the guide: an unnamed work started after an equal producing
  setup work also raises, since the two positions cannot be told apart.
- **Pre-replay inputs (seventh review of PR #188, user ruling option A).** A target whose setup
  work matched but which recorded an input before the replay passed the check; its replay session
  then held no setup expectations, and `Diagnostic` applied an initial command's async message twice
  (`[9; 2; 5; 5]`). A matching target now also has recorded no entry before the replay when the
  journal's setup work made a recorded input: `Journal.replay` raises `JournalReplayException` on the
  `Setup` entry in both modes, naming the condition. A journal whose setup work made no recorded
  input still replays into a target that took inputs, including a second replay into one graph.
- **Producing setup entries without their `Setup` entry (eighth review of PR #188).** The
  pre-replay check ran only on a `Setup` entry, so a slice of entries after a position that held a
  `Produced` entry of setup work skipped it, and `Diagnostic` applied the initial command's message
  twice (`[9; 2; 5; 5]`, and `[2; 5; 5]` for a second replay into one graph). The check now runs
  whenever the entries hold an input of setup work: it raises on the `Setup` entry when present,
  and otherwise on the first such `Produced` entry, with a reason that names no setup work.
- **Setup inputs without a `Setup` entry (ninth review of PR #188, user ruling "Raise on it").** A
  slice without its `Setup` entry replayed into a fresh target whose setup works sit in a different
  order applied a setup input twice under `Diagnostic` (`[2; 5; 5]`). `Journal.replay` now raises
  `JournalReplayException` in both modes whenever the entries hold a `Produced` entry of setup work
  and no `Setup` entry, on the first such entry, with the reason "the entries hold an input of setup
  work and no Setup entry; a tail replay needs the journal's Setup entry". This supersedes the
  earlier "Entries with no `Setup` entry match every target": that holds only for entries with no
  input of setup work. A tail replay of such entries waits on #197, which carries the `Setup`
  record with the snapshot.
