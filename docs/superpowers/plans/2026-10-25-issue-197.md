# Issue #197: journal snapshot plus tail restore over #68's stored-state format

Branch `issue/197`, cut from `origin/integration/issues` (b3f02951, the merge of #210); the PR base is
`integration/issues`. The branch is never rebased or force-pushed: when `origin/integration/issues` moves, merge it
into `issue/197` and push normally (`git push -u origin issue/197`).

## Goal

Restore a graph from a #68 snapshot taken at a journal position, then replay the journal entries after that position.
The snapshot is the set of `StoredRecord`s a `PersistSession` saved through `IStateStore` (#210), and the position is
the `$ranvier/position` record the session saves last in each `SaveMany` when the graph's journal is
`session.Journal`. `PersistSession.Position` exposes it after a load.

## Acceptance criteria (copied from the issue)

1. Restoring a #68 snapshot taken at a journal position and replaying the later entries gives the same values for
   every keyed input and every memo as an uninterrupted run. This is checked by a property test over sequences of
   external writes, settles and failures.
2. The same restore works in diagnostic and re-enactment replay modes.
3. Fable: the restore test passes under `build.fsx -- test-fable`.
4. The journal guide's restore section documents the snapshot API.

## Binding decisions (user, 2026-10-25)

- Build on #210's `Ranvier.Persistence`: restore from a `PersistSession` loaded at a position, then replay the journal
  entries after that position with `Journal.replay`, in both modes.
- `src/Ranvier`'s untraced IL stays unchanged unless the restore genuinely needs a core change; a core change records
  its reason here and in the PR. This design needs none (see Design).
- The residual buster race between two sessions is accepted for v1.
- Docs extend `guide/journal.md`'s restore section and `guide/persistence.md`; no new page (a new page would need a
  `Menu.page` entry in `docs/Site.fs`).

## Design

The work lives in `src/Ranvier.Persistence`. `src/Ranvier` is unchanged: the replay filters and rewrites
`JournalEntry` records (a public record) and calls the public `Journal.replay`; the restored source state is applied
inside the public `Journal.derived`, so it records no entry.

### What a snapshot must hold

Criterion 1 covers every keyed input, and the property's inputs include an async source's settles and failures.
#210 persists signals, keyed collections and tracked reads, but no async source, so a snapshot cannot hold a
source's `Ready` value or its failure. Every keyed input of the restored graph must be persisted under its journal
key (#166's stable key and #68's application key are one key space); the guide states this requirement, since the
package cannot see the graph's journal registrations (`JournalRecorder` is internal to `Ranvier`).

### `Persist.source`

```fsharp
val sourceKey: key: string -> codec: PersistCodec<'T> -> PersistSourceKey<'T>
val source: session: PersistSession -> key: PersistSourceKey<'T> -> AsyncSource<'T>
```

Shaped like `Persist.signal` (session, key; a source has no fallback: with no record it starts pending). The key is a
`PersistSourceKey<'T>` declared by `Persist.sourceKey`, not a `PersistKey<'T>`: a key's loader decodes its record at load,
and a source record holds status frames, so a separate key type keeps `Persist.signal` and `Persist.source` from
reading each other's records (decided while implementing step 2). It makes an
`AsyncSource<'T>` in the current graph and owner, claims the key, and saves the source's status after each flush that
changes it:

- `Ready value`: one record whose payload is the `PersistFrames` encoding of `["ready"; codec payload]`, at the
  codec's version, so `PersistCodec` migrations apply to the value frame;
- `Failed error`: `["failed"; error.Message]`;
- `Pending`: the record is deleted (`MarkDeleted`), as a removed row is.

A restored source is settled or failed at creation inside `Journal.derived graph`, so the restore records no journal
entry and leaves the restored graph's journal empty before the tail replay. A restored failure is a
`PersistedFailure(message)` (a new exception type in `Types.fs`, alongside `PersistLoadException`), whose `Message`
is the stored message: the restored status equals the run's status by message, as a replayed failure's
`JournalReplayedFailure` does. The loader decodes the frames at load, so a malformed status record fails `loadAsync`
with `DecodeFailed` naming the key (and honours `DiscardUndecodable`), like every other record.

`Journal.keySource key codec` then binds the restored source to the journal, exactly as for a fresh one.

### `Persist.replay`

```fsharp
val replay: mode: ReplayMode -> session: PersistSession -> graph: Graph -> entries: JournalEntry seq -> unit
```

Argument order follows `Journal.replay mode graph entries`, with the session inserted before the graph (the session
supplies the position). With `session.Position = None` it is `Journal.replay mode graph entries`: the store held no
position, so the snapshot is the fallback state and the whole journal replays. With `Some p`:

1. The entries must hold a non-`Flush` entry with `Seq = p`; otherwise it raises `ArgumentException` naming `p`: the
   entries belong to another journal than the one the snapshot's session recorded.
2. The tail is the entries with `Seq > p`, in `Seq` order. The `Setup` entry (`Seq` 0) and every entry at or before
   `p` are in the snapshot.
3. A tail entry `Produced (started, index, call)` with `0 < started <= p` belongs to work started before the snapshot.
   The restored graph never re-runs it (its starting entry is not replayed), so the replay rewrites the entry's
   `Origin` to `External` and applies it in both modes; a re-enactment would otherwise skip it and lose the input.
4. A tail entry `Produced (0, _, _)` with `p > 0` is an input of setup work made after the snapshot. The restored
   graph's own setup work re-runs live and makes its inputs again from its first call, so the replay cannot apply it
   exactly once: `Persist.replay` raises `JournalReplayException` on that entry, before it applies any entry, with the
   reason "the entries after the snapshot's position p hold an input of setup work; a restore replays the inputs of
   work started after the position".
5. Entries with `started > p` keep their origin: the work re-runs in the restored graph after its starting entry is
   replayed, and `Journal.replay`'s existing matching applies to it.

The replay records the tail on the restored graph's journal with new `Seq`s from 1, and the session's wrapper stores
those new positions in later saves. A position therefore always refers to the journal of the graph that saved it;
the guide says so.

### Out of scope (v1, recorded in the guide)

- Setup work that made inputs before the position: the restored graph re-runs it on build, as any reload of a
  persisted app does (for example an `Mvu.withCmd` initial command fetching again).
- Inputs not persisted under their journal key: the restore has no record of them.
- The buster race between two sessions (user ruling).
