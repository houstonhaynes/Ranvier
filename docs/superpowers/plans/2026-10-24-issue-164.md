## Current state (2026-10-24)

- Tracing is a compile-time switch: `RanvierTrace=true` defines `RANVIER_TRACE` and compiles `TraceEvents.fs`, `TraceSite.fs` and `TraceModel.fs` into the library (`src/Ranvier/Ranvier.fsproj`). It defaults to true in Debug and false in Release (`Directory.Build.targets`). There is no runtime toggle, so "equivalent traced and untraced graphs" means the same workload source compiled twice.
- The log is an unbounded `ResizeArray<TraceEvent>` per graph (`TraceLog`, `src/Ranvier/Trace.fs`); `Trace.events` copies it with `ToArray` on every call.
- The signal maps consume history incrementally by calling `Trace.events` and slicing `events[read..]` (`docs/maps/SignalMap.fs`, around lines 1020 and 1110). That full copy per read is the incremental-consumption baseline #165 replaces with cursors.
- Existing infrastructure:
  - `bench/Ranvier.Benchmarks`: BenchmarkDotNet 0.15.8, `MemoryDiagnoser`, Markdown and JSON exporters into `docs/.ai/benchmarks/results`. Release, so untraced.
  - `bench/Ranvier.Counters`: scenario worker shared with the Fable harness (`Workloads.fs` is linked into `fable/Ranvier.Counters`). It reports bytes/op and gen-0 collections everywhere, and instructions and CPU time on Linux. `perf build` / `perf ab` / `perf compare` in `build.fsx` gate base against head, untraced, in CI.
  - `fable/Ranvier.Counters`: the Node.js run of the same workloads. Its project pins `<RanvierTrace>false</RanvierTrace>`.
  - `examples/Fable.Ranvier.Playground/benchmarks/frameworks`: the Playwright Chromium harness (`keyed-rows.mjs`, `keyed-heap.mjs`).
- In a traced build, `Workloads.newGraph` keeps every graph it creates (`created`) for `Reconcile.fs`, which compiles only under `RANVIER_TRACE && RANVIER_COUNTERS`. A traced run without counters keeps every graph and log alive for the whole process, which skews heap and GC figures.
- The only traced cost figures on record are two zero-allocation tests: ~123 B/op for an equal write and ~516 B/op for a write that marks three memos (`docs/.ai/RESEARCH-graph-transparency.md` §3.6).

## Design

### Decisions

1. **.NET time, throughput and allocations come from BenchmarkDotNet with two jobs.** A new `Trace` category in `bench/Ranvier.Benchmarks` runs each workload under two jobs that differ only in `MsBuildArgument "/p:RanvierTrace=false"` and `"/p:RanvierTrace=true"`, with the untraced job as the ratio baseline. BenchmarkDotNet builds each job's project separately, so one source file gives both variants under one harness, with the `Mean`, `Op/s`, `Allocated` and `Ratio` columns the suite already reports. This is the existing framework; nothing new is introduced.
2. **Trace-only operations compile under `#if RANVIER_TRACE`** in their own benchmark class that carries a traced-only config, parameterised by history length (1,000, 10,000 and 100,000 updates).
3. **Retained memory and history growth come from a `trace-growth` probe in the counter bench**, in a file shared with the Fable harness, so .NET and Node run the same graph. It runs sustained updates on one graph, and at each checkpoint reports the update count, event count, retained heap bytes after a full collection, and the time to take `Trace.events`, `Trace.snapshot`, `Trace.dumpText` and an incremental tail read. The untraced build runs the same probe and reports the untraced retained heap at each checkpoint; the difference is the log's retained cost. The probe's derived figures (events per update, retained bytes per event, a least-squares slope across checkpoints) are a pure function with unit tests in `bench/Ranvier.Counters.Tests`.
4. **The incremental-consumption baseline is the signal maps' pattern:** `Trace.events` followed by a slice from the last read count. #165 will add a cursor read; this probe keeps the same row so the two compare directly.
5. **Fable runs under Node.js through the existing harness**, compiled twice: the harness project's pin becomes `Condition="'$(RanvierTrace)' == ''"`, so `RanvierTrace=true` in the environment compiles a traced harness. `perf build` already sets `RanvierTrace=false` explicitly, so the CI measured build is unchanged.
6. **Chromium figures come from the Playground's framework harness** (`keyed-rows`, `keyed-heap`) against a traced and an untraced Playground build. Chromium is the last measurement step: the core cost model rests on the .NET and Node rows, and Chromium confirms that the Node ratios hold in a browser.
7. **Reproduction is a `build.fsx` command, `perf trace OUT`**, in line with `perf build` / `perf ab`: it builds both variants of the counter worker and the Fable harness, runs the counter scenarios and the growth probe for both, runs the BenchmarkDotNet `Trace` category, and writes the results with a `versions.json` (dotnet, Fable, fable-library, source revision, OS, CPU). Results are committed under `docs/.ai/benchmarks/tracing/<sha>/`.
8. **The budget is documented in `docs/content/benchmarks/tracing.md`.** Its shape: the untraced build stays byte-for-byte identical to the untraced baseline in bytes/op and library counters (the existing perf gate); traced time and allocation ratios per workload may not exceed the measured ratio plus a stated headroom; retained bytes per event and events per update may not exceed the measured values plus headroom; export and incremental-read costs are stated per 1,000 events. The headroom figures are set from measured run-to-run spread, not chosen in advance.
9. **Existing gates:** the untraced library is not edited by this issue. `dotnet fsi build.fsx -- test`, the traced test stage, and `counters.ps1 -NoPmc` parity against `integration/issues` are the gate.

### Workload set

Every workload runs traced and untraced. Steady-state methods measure updates on a prebuilt graph; construction methods build and dispose a graph per invocation, so the two are reported separately.

| Workload | Steady state | Construction |
| --- | --- | --- |
| `signal` | write one signal with one observing effect | create a graph with one signal and effect |
| `memo` | write a signal read by one memo and effect | create the same |
| `chain` | write the head of a 4-deep memo chain | create the chain |
| `fanout` | write a signal read by 64 memos | create the fan-out |
| `cutoff` | write a value the memo maps to an equal result | — |
| `batch` | 10 writes inside one `batch` | — |
| `dispose` | — | create and dispose a root of 1,000 effect rows |
