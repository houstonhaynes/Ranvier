## Core and view state

This is adapter work over the core; it adds no view code and no core API.

**Core primitives used:**

- `Graph` with `ThreadPolicy.Guarded` and a `SynchronizationContextDispatcher` (via `GraphOptions.WithDispatcher`): the host thread owns the graph, and a touch from a transport thread raises.
- `Graph.DispatchAsync` (#167): the only path from a transport thread into the graph; every tool body runs inside it and its task carries the result or the fault back.
- `Memo` / `createMemoWithComparer` and the graph's equality policy: each exposed value is a reader whose cutoff decides whether it changed.
- `createEffect` under an `Owner` from `createRoot`: one publication effect reads every exposed reader, so a flush produces one consistent snapshot, and `batch` coalesces writes into one effect run.
- `Mvu.Dispatch` (Ranvier.Elmish): applies a decoded message on the graph thread.
- `Trace.why` / `whyNot` / `waitingOn` / `snapshot` / `checkpointOf` / `eventsSince` and `TraceContract` + `TraceJson` (#165, #166): provenance results, serialised by the stable contract, compiled only under `RANVIER_TRACE`.

**View-owned state:** none. Adapter-owned state, none of which has a core equivalent: the immutable published snapshot (`{ Version; Values }`, swapped atomically so reads never enter the graph), the last encoded JSON per exposed value (to name which resources changed in a publication), the registry of exposed names, codecs, message decoders and traced node names, and the MCP subscription set.

## Current state (2026-10-24)

- `Graph.DispatchAsync(Func<'T>)` and `(Func<'T>, CancellationToken)` exist (`src/Ranvier/Core.fs`); from another thread they queue on the inbox and complete after the work runs on the drain.
- With no `SynchronizationContext`, the default dispatcher is `ManualDispatcher`: the inbox drains only on `Graph.Pump`. A console MCP server has no context, so the adapter needs its own graph thread.
- `Mvu<'Model,'Msg>.Dispatch` queues from another thread; there is no awaitable form, so the adapter awaits `Graph.DispatchAsync (fun () -> mvu.Dispatch msg; version)`, which runs inline on the graph thread and returns after the flush.
- The `Trace` module's queries exist only under `RANVIER_TRACE`; `TraceJson` writes `state`, `why`, `whyNot`, `waiting`, `runs` and `lookup` documents with `Schema = 3`.
- No MCP code exists. The C# SDK package `ModelContextProtocol` is at 2.3.0 on nuget.org (stable 2.x line), with stdio and stream transports and an `McpClient` usable in-process.

### API shape (F#-first, matching Ranvier conventions)

Rationale: the issue leaves the shape open. Ranvier's conventions are a BCL-delegate-friendly class for stateful hosts (`Graph`, `Mvu`) and `[<RequireQualifiedAccess>]` modules of constructors; the adapter follows them.

```fsharp
type GraphHost =                                  // IDisposable; owns a thread and a Guarded graph
    static member Start : setup: (Graph -> 'App) -> GraphHost<'App>
    member Invoke : work: ('App -> 'T) -> Task<'T> // Graph.DispatchAsync on the host graph
    member GraphThreadId : int

type Codec<'T> = { Encode: 'T -> JsonNode }
type MessageDecoder<'Msg> = JsonElement -> Result<'Msg, string>   // Error = explicit rejection

module Expose =                                   // called inside the setup, on the graph thread
    val value : name: string -> codec: ('T -> JsonNode) -> reader: (unit -> 'T) -> Exposure -> unit
    val messages : mvu: Mvu<'Model,'Msg> -> decoders: (string * MessageDecoder<'Msg>) list -> Exposure -> unit
    val node : name: string -> node: INode -> Exposure -> unit           // traced introspection target

module McpAdapter =
    val tools / resources registered on an IMcpServerBuilder or an McpServerOptions
```

Names stay provisional until step 3 proves them in the REPL; the plan records any change.

### MCP surface

- Resources: `ranvier://state` (whole snapshot: `version`, `values`) and `ranvier://state/{name}` per exposed value; `resources/subscribe` supported; `notifications/resources/updated` sent for `ranvier://state` and for each value whose encoded JSON differs from the previous publication.
- Tools: `snapshot` (version + values, read from the published snapshot without entering the graph); `dispatch` (`{ message: string; args: object }`: unknown name or decoder `Error` returns an MCP tool error and dispatches nothing; `Ok` dispatches on the graph thread and returns the snapshot version after the flush); `wait_version` (completes when the published version reaches a value, with a timeout).
- Traced builds only (`#if RANVIER_TRACE` in the adapter, so an untraced build has no such tools to list): `trace_state`, `trace_lookup` (node resolution by `TraceAddress`), `why`, `why_not`, `waiting_on` over exposed node names, each returning the `TraceJson` document. They run inside `GraphHost.Invoke`.

### Graph ownership

Transport threads hold no `Graph`, `Signal` or `Memo`; they reach the graph only through `GraphHost.Invoke`. Snapshot reads use the published immutable value (`Volatile.Read`). A test proves a direct touch from a pool thread raises under `Guarded`, and that every tool body observes `Environment.CurrentManagedThreadId = GraphThreadId`.

### Publication

A single effect, created in the host's root after setup, reads every exposed reader, encodes each value, and when any encoding differs from the last publication, increments the version, swaps the snapshot and raises the notifications. A memo's cutoff stops an unchanged value from re-running the effect; `batch` writes produce one run; a re-run whose encodings all match the previous publication publishes nothing. Registration closes once the effect exists.

### Validation experiment

Defect: the sample's defective build reads the discount through `Peek` (untracked) inside the total memo, so a discount change leaves the total stale. Expectation, checked by independent tests: the total equals the sum of line prices less the active discount after any message sequence. Two workflows with the same model and task prompt: baseline (source, build, tests) and experimental (the same plus the MCP server: `why` / `why_not` on the total). Record per run: success, tool calls, repair iterations, total tokens, wall-clock time, independent test verdict. Results and protocol in `docs/.ai/research/2026-10-24-issue-168-experiment.md`, negative findings included; no conclusion from a single success.
